# 五个交互场景的可行性评估

- 日期：2026-10-27
- 输入：用户口述的 5 段场景（实际含 6 个诉求：①选记录分析 ②简单数据+引导 ③计划生成 ④查看计划 ⑤知识问答 ⑥水平评估）
- 结论口径：**"可实现" = 现有代码能拼出来 / "需小改" = 缺通道但部件都在 / "不可实现" = 缺业务模块**
- 关联：[去路由化重构方案](./2026-10-27_对话Agent_去路由化重构方案.md)（choices 通道是它的 UI 面）、[分层节点 IO 说明书](./2026-10-27_对话Agent_分层节点IO说明书.md)

---

## 一、总判断

**3 个今天就能跑通，1 个需小改（约 1.5 天），2 个卡在同一个业务模块（AGT-F）。**

| # | 场景 | 判断 | 阻塞点 |
|---|---|---|---|
| ① | 数据分析 → 追问"哪一次"→ **记录列表** → 点选 → 生成 → **深度分析入口** | **需小改**（约 1.5 天） | 缺“结构化选择”通道（响应/请求/前端三处），部件全在 |
| ② | 问数据 → **只给简单数据 + 引导深度分析** | **已可实现** | 只差引导文案与入口字段（同 ①） |
| ③ | 训练计划生成 → 追问"目标"+ **目标选项** → 生成 → **确认** | **不可实现** | 计划域模型 + 处方硬门 + 写路径（AGT-F，前置 P6） |
| ④ | 问训练计划 → 展示并解释当前计划 / 没有则引导生成 | **不可实现** | 同上（连"计划"这个实体都还没有） |
| ⑤ | 骑行知识问答 → 调知识库 | **已上线** | 可打磨：别名表、未覆盖零模型话术（AGT-C2） |
| ⑥ | 骑行水平 → 调数据查询+知识库 → 评估后回答 | **已上线** | 可打磨：越界评级硬门（AGT-C3）、演示数据不足 42 天 |

**最关键的发现：①③ 的"展示选项让用户选"其实是同一个机制。** 把它做成一个通用能力（下称 **choices 通道**），①的全部 + ③④ 的前两步就一起解决了。真正独立的硬骨头只有一块：**计划域**。

## 二、逐场景拆解

### ① 骑行数据分析：追问 → 记录列表 → 点选 → 分析 → 深度分析入口

**现在能做什么**
- 追问话术**已有**：`resolveRideAnchor` 无锚点时返回"你说的「这次」是指最近一次（10月5日）的骑行，还是其他某一次？可以直接告诉我日期。"（零模型）
- 记录清单**数据已在手边**：`app/chat/page.tsx` 本来就 `listRides(userId)`，只是被 `buildChatHomeSnapshot` 丢掉了；工具侧 `get_ride_history` / `find_ride` 也能返回带 `rideId + rideDateLabel + claims` 的行
- 深度分析**链路已完整**：`/api/ride-analysis`（V1 v0.4 candidate + `?ai=v2` 引擎，带 session/ownership 校验与演示记录支持），前端组件 `RideAiAnalysis` → `InterpretationSheet`（抽屉形态，接收 `rideId / title / dateLabel / engine`）
- 点选后能让模型答：`get_ride_context` 已支持任意 `rideId`

**缺什么（三处，缺一不可）**

| 缺 | 具体 | 位置 |
|---|---|---|
| 1. 响应带候选 | 目前响应只有 `reply/trace/validation`，没有结构化候选列表。要加 `choices: [{id,label,sublabel,kind}]` 与 `deepAnalysis: {rideId, dateLabel}` | `publicChatAgentResult` + `route.ts` |
| 2. 请求能带选择 | `/api/chat` 的键白名单只有 `text/summaries`，多一个键就 400。要加 `choice?: {kind:"ride", rideId}` | `route.ts:90` |
| 3. 前端能渲染 | `ChatHome` 只渲染气泡，没有"可点选列表"组件；快照里也没有记录列表 | `app/components/chat-home.tsx`、`chat-home.ts` |

**深度分析入口怎么做**（推荐）：不要跳页，**在当前对话上叠 `InterpretationSheet` 抽屉**——对话上下文不丢，且组件已存在、只需传 `rideId + dateLabel`。走 `engine="v2"` 时延迟十几秒，抽屉内已有 loading 三段式。

> 注意一个真实约束：点选必须传 **`rideId`**，不能只传日期。同日两条记录在现有"按日期查 → 取最晚出发"的逻辑下会撞车。这也是重构方案里 `rideRef` 的由来。

---

### ② 问数据 → 只给简单数据 + 引导深度分析

**这条其实已经是现状**，而且它把一个"缺陷"变成了"设计"：

- 现状 `currentRideDimensions(text)` 在没提到功率/心率/踏频/爬升时返回 `["summary"]`，只有距离/时间/平均速度/最高速度。之前这被记为"解读取数贫瘠"，但**按你现在的分层设计，它恰好是对的**：轻问 → 轻答（快、省钱），重问 → 走深度分析工作流（慢、但富证据）。
- 需要补的只有两件事：① 回复末尾固定引导"想看完整解读，点开深度分析"；② 响应里带 `deepAnalysis` 字段让前端渲染按钮。

**一个必须守住的边界**：引导语不能说成"我给你做了深度分析"。轻答只说数据，深度结论一律留给工作流。

---

### ③ 训练计划生成：追问目标 → 目标选项 → 生成 → 确认

**现在是什么状态**：`training_plan` 进 `runChatAgent` 的确定性模板分支，回一句"正在自主 Agent 改造路线图中"。零工具、零模型。**AGT-F 还在 Backlog，前置是 P6 决策**。

**缺 6 件，且有先后依赖**

| # | 缺 | 说明 | 能否先做 |
|---|---|---|---|
| 1 | 要素追问 + 目标选项 | 目标/期限/每周可用时间/基线四要素 | **能**（复用 choices 通道） |
| 2 | 取数 | 复用现有 5 个工具（档案/负荷/历史/路线/KB），无需新只读工具 | **能** |
| 3 | 计划生成 | 开放生成（非模板填充），产出 `Plan{weeks[{sessions[{day,type,durationMin,intensityZone,targetWatts,targetHr,purpose}]}]}` | 需 AGT-F |
| 4 | **处方硬门** | 强度不越 maxHR/FTP 关系、周负荷增幅上限、每周≥1 恢复日、伤病禁忌→`safety_stop` | 需 AGT-F（**不可省**） |
| 5 | 计划实体 | Plan / Session 落库（当前完全没有"计划"表） | 需 AGT-F |
| 6 | 确认令牌 | 全项目首个**写路径**，未确认不得生效 | 需 AGT-F |

**为什么不能"先生成再说"**：训练处方是唯一"说错会让人受伤"的输出。数字白名单能保证数字有出处，保证不了"这个处方合理"——后者只能靠规则化硬门 + 人工确认。放行门已经定死：**采纳率 ≥60%、处方硬门违规 = 0**。

---

### ④ 问训练计划 → 展示并解释当前计划 / 没有则引导生成

**比 ③ 更靠后**：现在连"计划"这个实体都不存在，没有表、没有 API、没有 `get_active_plan` 工具。所以：
- "没有计划 → 引导生成" — **现在就能做**（一句话术而已，价值有限）
- "展示并解释当前计划" — **不可实现**，依赖 ③ 的 5、6

建议：先做"引导生成"这一半（1 小时），把交互入口占住；等 AGT-F 出来再接"展示"。

---

### ⑤ 骑行知识问答

**已上线**，链路是 `kb_qa → search_knowledge_base`：
- 7 个知识维度（配速执行/爬坡表现/心率负荷/功率输出/强度与训练负荷/踏频策略/多传感器协同）
- 输入 `dimensionIds[]` 或 `keywords[]`（至少一个），`maxEntries ≤3`，单条 `excerpt ≤600 字`
- 硬门：必须调工具；`knowledgeIds` 必须 ⊆ 本轮返回条目；`capabilityKeys` 必须空

**可打磨两处**（AGT-C2）：① 别名表（乳酸阈/LT、甜区/sweet spot、VO2max/最大摄氧量、踏频/转速）——现在 `BND-K02 VO2max`、`BND-K03 甜区` 走"未覆盖"，要先区分"真没这条"和"别名没映射"；② 未覆盖改**零模型统一话术**（现在靠 prompt 一句约束，措辞不可控，且无命中时是编造风险最高处）。

---

### ⑥ 骑行水平评估

**已上线**，`level_assessment → 5 件 catalog`：健康档案（体重/maxHR/FTP）、训练负荷（CTL/ATL/TSB）、历史统计、路线概要、知识库。

**两个必须交代的现实**
1. **不许评级**：现在是 prompt 约束"只能做事实叙事"，**校验层还没有兜底**；AGT-C3 计划加 `OUTPUT_ASSESSMENT_OVERREACH`（完整短语匹配：业余中级/进阶骑手/精英/前百分之…），不做单字匹配以免误伤"中高强度"。
2. **演示环境会缺一块**：PMC 要求 ≥42 天跨度 + ≥10 个负荷日，而现在只有 4 条演示记录（7-18 ~ 10-05 跨度够，但负荷日只有 4 个）→ 必然返回 `INSUFFICIENT_LOAD_DAYS`。**这是正确行为**，但演示时要准备好"如实说负荷算不出来，只能给里程/心率层面的观察"。

## 三、两个真缺口

### 缺口 A：choices 通道（结构化选择）

一条能力，解决四个诉求：①选记录、③选训练目标、④选计划槽位、以及"当前分析对象"常驻指示器。

**合同草案**
```jsonc
// 请求（在现有 text/summaries 之外新增）
{ "text": "...", "summaries": [...], "choice": { "kind": "ride", "id": "r-0820" } }

// 响应（新增两个可选字段，旧前端忽略不影响）
{
  "reply": "你想分析哪一次？我在下面列了最近的几次。",
  "choices": [
    { "id": "r-1005", "label": "10月5日", "sublabel": "30.4 km · 1h12m · 有心率", "kind": "ride" },
    { "id": "r-0820", "label": "8月20日", "sublabel": "31.1 km · 通勤", "kind": "ride" }
  ],
  "deepAnalysis": { "rideId": "r-0820", "dateLabel": "8月20日" }
}
```

**三个设计口径**
- 列表密度：**最近 5 条 + "更多"**；每条必须带"有无功率/心率"，否则用户点了才发现没数据
- 排序：出发时间倒序（与"最新"口径一致）
- 与文本澄清并存：点选优先，用户手打日期仍然有效（现有确认轮保留）

> 这条通道同时是重构方案里 `rideRef` 的 UI 面——**建议合并设计一次做完**，不要先做文本澄清再返工。

### 缺口 B：计划域（Plan / Session / 硬门 / 确认）

见 ③④。这是唯一需要新业务模块的地方，工作量以"里程碑"计（不是"接个工具"）。

## 四、交互层必须定的 5 个细节

| # | 细节 | 建议 |
|---|---|---|
| 1 | 记录列表多少条、显示什么 | 最近 5 条；每项：日期 + 距离 + 时长 + 有无功率/心率。多了折叠 |
| 2 | 深度分析入口形态 | **抽屉**（复用 `InterpretationSheet`），不跳页、不丢对话；走 v2 引擎时提示"约 10~20 秒" |
| 3 | 训练目标枚举 | 提升 FTP / 完成首次百公里 / 减重 / 备赛（需选赛事与日期）/ 保持健康 / 其他（自由输入） |
| 4 | 计划确认流 | 生成后**先展示、不生效**；"确认生效"二次确认并落库留痕；未确认前只在本次会话可见 |
| 5 | 所选记录缺指标时 | 不能只说"没有数据"，要指出缺哪个维度（现有 `limitations` 字段可承载） |

## 五、建议的落地批次

| 批次 | 内容 | 规模 | 产出 |
|---|---|---|---|
| **批次 1** | choices 通道（响应/请求/前端列表）+ 记录列表 + 点选 + `deepAnalysis` 入口 + 简单数据引导文案 | 后端 ≈1 天、前端 ≈0.5~1 天 | **场景 ①② 完整跑通** |
| **批次 2** | KB 别名表 + 未覆盖零模型话术；评估越界硬门；演示数据补到 ≥42 天/≥10 负荷日 | 3~5 天（随 AGT-C2/C3） | **场景 ⑤⑥ 从"能用"到"稳"** |
| **批次 3** | 计划域（要素追问 + 生成 + 硬门 + 实体 + 确认令牌 + `get_active_plan`） | AGT-F 一个里程碑（前置 P6 + 交互 PRD） | **场景 ③④** |

## 六、三个要提前说的风险

1. **点选必须用 `rideId`，不能只用日期**：同日两次骑行在"按日期 → 取最晚出发"的现有逻辑下会静默选中错的那条。这条不解决，"选任意一次"就是假的。
2. **深度分析是另一条链路**：`/api/ride-analysis` 走 `RIDE_MODEL_V2_*` 配置（骑后解读），与对话链路的 90s 预算、provider 配置完全隔离。好处是互不影响；坏处是**同一句话在两处可能给出不同结论**（对话轻答 vs 工作流深答），文案上要明确区分"摘要"与"完整解读"。
3. **计划生成的风险等级最高**：它是全项目第一个同时具备"写操作"和"可能伤人"的输出。硬门与确认令牌不是体验优化，是准入条件。

---

## 七、一句话回答

**能实现，但不是同一个难度**：⑤⑥ 已经在跑，② 只差一句引导，① 差的是一条"让用户点选"的通道（约 1.5 天，且正好是重构方案里 `rideRef` 的 UI 面），③④ 差的是一整个计划域（AGT-F，必须带处方硬门与确认制）。

优先级建议：**先做 ① 的 choices 通道**——它一份投入、四处受益（选记录 / 选训练目标 / 选计划 / 当前分析对象指示），而且是 ③④ 的前置交互骨架。
