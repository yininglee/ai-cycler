## 4. 缺陷清单（19 项，按性质分三类）

### 4.1 产品缺陷（12 个，影响真实用户）

| # | 缺陷 | 根因 | 修法 | 验证 |
|---|---|---|---|---|
| 1 | 整轮耗时 227s 仍不返回 | 单次 race 超时不覆盖 body 读取 | 双保险（fetch + body 各自 race） | 预算测试 |
| 2 | `windowDays` 越界判非法 | 校验器把"超上限"当"非法输入" | 钳制到上限 + limitations 注明 | `chat-b5-window-clamp` |
| 3 | 枚举参数被模型填成数组 | catalog 用 JSON 数组展示枚举候选 | 显式写"单选字符串（不是数组）" | ORCH-03/11/13/17 |
| 4 | claimId 编号被当数据数字 | `chatNumberTokens` 把 `claim:loop:1:1` 的 1 提取为数字事实 | 剥引用标记后再提取 | `chat-numeric-evidence` 单测 |
| 5 | 修复轮不受整轮时间预算 | elapsed 检查只在首轮 | 修复轮也检查 | 156.6s 案例回归 |
| 6 | 无任何记录时空锚点启动失败 | 空锚点直接判不可用 | 全局工具先行启动循环 | 边界集 `no_records` 9/9 |
| 7 | 用药建议未拦截 | 红线只覆盖急症/危险骑行 | 新增 `MEDICATION_ADVICE` | 边界集 `safety` 18/18 |
| 8 | 零工具合法拒答无出口 | 校验要求"零工具必有证据" | 四条严条件放行（证据全空 + 无数字 + 能力说明措辞 + 无事实断言） | BND-S06 |
| 9 | `get_capabilities` 无可引用证据 | `evidenceKind: "capabilities"` 且 `hasUsableEvidence: false` | 每个能力生成 claim（value 1/0） | ORCH-21 3/3 |
| 10 | `caps` 上限 8 < 合法值 18 | `uniqueEnumValues(..., 8)` | 放宽到全集 | ORCH-09 3/3 |
| 11 | `get_ride_history` 缺 `rows[].claims` | numericFacts 只放总计 | 补逐条明细数值 | ORCH-05 3/3 |
| 12 | `get_training_load` 缺 `ridesWithoutTss` | 跳过记录数只在 limitations 字符串里 | 结构化 + 进白名单 | ORCH-05/16 |

**共性**：#9~#12 都是"**工具产出了事实，但没把它做成可引用的证据**"。模型的回答本身正确，却因为没有合法引用路径被判越权——**这类缺陷在评测里表现为 `NO_MATCH` / `REPAIR_FAILED`，极易被误读成"模型能力不足"**。

### 4.2 评测资产缺陷（3 个，影响评测可信度）

| # | 缺陷 | 后果 |
|---|---|---|
| 13 | 编排集完全跳过 L0 | 负例（写操作、注入）本该零模型拦停，却进 L2b 循环去调数据工具 → 必然失败（ORCH-19/20 各 3/3 失败） |
| 14 | 判分要求"必须 validated" | 负例的正确交付是零模型确定性拒绝（`template` + 无 fallbackCode），要求 validated 等于要求模型答不该答的 |
| 15 | 用例措辞触发锚点澄清 | "这次"在多记录下触发 `TOOLS_ANCHOR_CLARIFY`，被记为编排失败（15 次假失败） |

### 4.3 用例期望错误（4 处）

| 用例 | 原期望 | 为什么错 | 修正 |
|---|---|---|---|
| ORCH-02 速度比较 | 必须给出比较结论 | `avgSpeedMps` 的 `routeSensitivity = high`，跨路线比速度在领域层就被禁止（`ROUTE_SCOPE_REQUIRED`）——**正确答案是"不可比"** | `allowDegraded` |
| ORCH-17 三年前记录 | 必须调 `get_ride_history` | 窗口上限 365 天，三年前数据不存在；`find_ride(max)` + 说明窗口限制同样正确 | `requiredAnyOf`（v0.2） |
| ORCH-19 删除记录 | 走 L2b 编排 | 应在 L0 零模型拒绝（`WRITE_NOT_SUPPORTED`） | 负例接入 L0 |
| ORCH-20 注入 | 走 L2b 编排 | 应在 L0 零模型拦停（`PROMPT_INJECTION`） | 负例接入 L0 |

**共同点**：把"**我们预想的实现路径**"当成了"**什么算答对**"。四次修正都不是放宽标准，而是把实现假设换成行为断言。

## 5. 方法论：三次把环境问题误判为产品问题

这是本次 B5 最重要的教训。三次误判都发生在"看到分数低 → 急着解释数字"的时候。

| # | 我当时的结论 | 真相 | 怎么发现的 |
|---|---|---|---|
| 1 | "服务波动（夜间高峰）" | **超时设置错配**：单次 25s 上限，而成功调用的 headers p90 = 22.1s、max = 24.9s | 测服务端：裸请求 1.6~2.1s、完整 prompt 5.1s（5/5 成功） |
| 2 | "网络污染（`failurePhase: headers`）" | **同一原因**：16 次失败全是 `totalMs = 25002ms`（我们自己 timeout 到点），**无一次 85.9s 的 TCP 超时** | 拉出 16 次失败的 `totalMs` 明细 |
| 3 | "V4.1-Flash 真实水平只有 77.8%" | **三重叠加**：缺 `ridesWithoutTss`（5 次）+ ORCH-17 期望过僵（3 次）+ 平台限流（一度打到 34.9%） | 逐例诊断 + 单例复现 + `sleep=0` 极限测试 |

**沉淀的纪律**：

1. **看到失败先问三个"不是"**：这是环境问题吗？这是评测问题吗？这是用例问题吗？——然后才问"这是产品问题吗"。
2. **判网络/平台类失败**：看 `errorCode` + `totalMs` 是否恰好等于 timeout 值（= 误杀）还是 85s 级固定值（= TCP 超时）。`failurePhase` 只说明"卡在等响应头"，**不区分连接失败 / 服务端排队 / prefill 慢**。
3. **判用例期望**：问"两条路径是否产出等价正确答案"，而不是"两条路径是否都能跑通"。
4. **单例改善 ≠ 全量改善**：purpose 反向映射单例 +2、全量 -5（ORCH-11 从 1/3 掉到 0/3）。

## 6. 决定不做的三件事（及理由）

| 事项 | 决策 | 理由 |
|---|---|---|
| **合并 `get_ride_context` + `find_ride`** | **不实施** | ① 原始动机（工具选择误用 ~6 次/轮）已归零——四次"像工具选错"的失败根因分别是期望过僵、caps 上限、缺 `ridesWithoutTss`、缺 `rows[].claims`，**没有一次是工具设计问题** ② 方案只合这两个工具，而剩余 2 次失败缺的是 `get_route_overview`（明确不在范围）→ 合并也照样失败 ③ 成本 1 天 + 违反 P7 作废 v0.2 + 全基线重跑，收益上限 95-97% < 当前 96.8%。方案与复用判据见 [工具合并方案](开发规划/AGT-B_工具合并方案_ride_query.md) |
| **修 ORCH-11 的 2 次失败** | **接受不修** | 2/63 = 3.2%；只能靠 Prompt 强调分轮规则，而今晚已有三次"加引导反噬"实证：purpose 反向映射净亏 5 次、放开不可比 claim 诱发"完全一致"幻觉、分轮规则压崩 capabilities 路由 |
| **为不可比场景放开模型解释** | **已回退** | 曾让 `not_comparable` 的 claim 可引用 + Prompt 解释 → 模型答成「完全一致，没有变化」并**编造"相同路线"**（不可比 ≠ 相同，幻觉方向），且破坏 CHAT-13「首骑不可比无 claimId」契约。改为**零模型话术**按 `reasonCodes` 映射 |

## 7. 评测口径与基础设施

### 7.1 口径（对外陈述必看）

| 项 | 口径 |
|---|---|
| 编排合法率 | 必需工具齐全 + 无禁止工具 + 参数全合法 + **最终交付成功**（`validated`/`repaired`） |
| 负例合法 | `template` + 无 `fallbackCode`（L0 零模型拦停）即为正确交付 |
| `allowDegraded` | 仅用于"工具选对但领域规则判定无可用证据"（ORCH-02 速度不可比）；启用时跳过"必须交付" |
| `requiredAnyOf` | 多条合法路径任一命中；**使用条件 = 两条路径产出等价正确答案** |
| 边界降级 | 无数据说无数据、未覆盖说明未覆盖、不编造数字 |

### 7.2 基础设施（B5 期间补齐）

| 设施 | 作用 |
|---|---|
| **provider 分阶段计时**（`onTiming`） | 回传 `headersMs` / `bodyMs` / `failurePhase` / `errorCode`；**这是"网络 vs 平台 vs 我方"归因的唯一可靠依据** |
| **限流退避重试** | `MODEL_RATE_LIMITED` 时 8s/16s/24s 退避，最多 3 次；日志 `↻`/`↺`；结果记 `rateLimitRetries`（**注：逻辑已实现，但 sleep=0 极限测试未触发限流，退避分支未被实测触发**） |
| **preflight 零模型校验** | 哈希 / 结构 / 工具名与代码枚举一致 / 证据形态覆盖；不调用模型 |
| 评测间隔 | 现需 **≥4s**——V4.1-Flash 单次 1.1s，间隔过密会撞平台限流 |

### 7.3 已知短板

1. **退避重试未实测**（见上）。
2. `steps` 落盘为 `null`（`eval/runs/*.json` 的 `steps` 字段未正确序列化），诊断时需靠 chat-trace 日志。
3. 边界集与编排集**共用同一 fixture**（22 条跨 90 天，数值已差异化：最近一次 56km/230W vs 历史 47~51.5km/193~211W）。
4. 时间敏感 flaky 测试 `latencyMs >= 30`（`candidate service`）在 CPU 竞争时偶发失败，单独跑通过。
