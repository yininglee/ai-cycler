# AI 骑行伙伴项目台账使用说明

> 建立日期：2026-08-14  
> 目的：让 Demo 搭建、测试、上线和持续迭代过程可恢复、可复现、可审计。

## 1. 为什么需要台账

AI 产品的运行结果不仅取决于代码，还取决于规则、数据 Schema、Prompt、扣子 Workflow、模型、参数和知识库。如果只记录“功能完成”，后续无法回答：

- 哪个版本产生了这条错误回答？
- 当时使用了什么数据、Prompt、模型和规则？
- 为什么决定加入或删除某项功能？
- 某个版本依据什么证据进入下一阶段？
- 用户反馈是否真的被处理并回归验证？

台账是项目的事实记录，不是为了增加管理工作。

## 2. 文件职责

| 文件 | 更新方式 | 用途 |
|---|---|---|
| `index.md` | 维护人工导航和事实源目录 | 可选导航；不承载新的项目事实，也非Codex每次必读 |
| `current-status.md` | 每次状态变化时覆盖更新 | Codex唯一恢复入口；当前阶段、阻塞、版本和下一项 |
| `progress-ledger.md` | 只追加，不重写历史 | 每次实施、测试、预览和验收的事实记录 |
| `decision-log.md` | 只追加；变更决定新增记录 | 产品、Agent、技术、范围和上线决策 |
| `eval/benchmark-report.md` | 按测试轮次追加 | 模型、Prompt、Workflow 基准测试结果 |
| `AI骑行伙伴-版本路线图与上线放行机制.md` | Gate 规则改变时版本化 | 阶段目标、放行、灰度和回滚规则 |

工作项验证放在`reviews/ITEM-*.md`，跨版本基准放在`eval/benchmark-report.md`，原始AI运行放在`eval/runs/`；进展日志只记录结果摘要和证据链接。

## 3. 后续协作方式

每个开发项都按以下闭环进行：

1. **选择工作项**：只选择一个可预览、可测试的小切片。
2. **开始前说明**：明确为什么做、范围、排除项、验收条件和风险。
3. **实现**：Codex 完成代码/配置/文档，保留现有用户修改。
4. **验证**：运行相应测试，记录真实结果；不能运行的部分明确写“未验证”。
5. **用户预览**：提供可访问页面、截图或文档，由用户检查。
6. **用户决定**：接受、要求修改、暂缓或取消。
7. **写入台账**：记录证据、版本、测试、反馈、决定和下一步。
8. **进入下一项**：未通过当前验收门，不自动扩大范围。

## 4. 工作项状态

| 状态 | 含义 |
|---|---|
| `PROPOSED` | 已提出，尚未同意进入实施 |
| `READY` | 范围与验收条件明确，可以开始 |
| `IN_PROGRESS` | 正在实施 |
| `READY_FOR_PREVIEW` | 实现和开发者验证完成，等待用户查看 |
| `CHANGES_REQUESTED` | 用户提出修改，尚未验收 |
| `ACCEPTED` | 用户确认达到本项目标 |
| `BLOCKED` | 存在明确外部阻塞 |
| `CANCELLED` | 已决定不做，保留原因 |

“代码已写完”不等于 `ACCEPTED`。需要用户预览的产品项，必须经过预览确认。

## 5. 最小记录字段

每次台账条目至少包含：元信息（日期/阶段/工作项/状态）、本次变化、证据链接和下一步。版本变化、用户反馈、风险、阻塞及`NOT_RUN/PARTIAL`仅在实际发生时增加，不保留空字段。

使用`RUN-YYYYMMDD-NNN`标识需要独立比较的测试或AI运行。AI运行至少关联：

`app_version + rules_version + schema_version + prompt_version + workflow_version + model_id + kb_version + case_id/request_id`

### 5.1 增量记录规则

台账采用“单一事实源 + 轻量引用”：

- `current-status.md`只保留当前快照，不保留完整历史叙事；
- `progress-ledger.md`每条日志只记录本次变化、真实验证摘要、用户动作和下一步；
- `decision-log.md`只记录决定、备选、理由、代价和重评触发，不复制测试报告；
- 工作项验证、跨版本基准和原始AI运行分别以`reviews/ITEM-*.md`、`eval/benchmark-report.md`和`eval/runs/`为准；
- 其他文档使用工作项、日志、决定或运行 ID链接到事实源。

新规则从优化记录之后生效；已有历史条目不删除、不静默改写。

## 6. 追加式规则

- `progress-ledger.md` 和 `decision-log.md` 的历史条目不删除、不静默改写。
- 发现旧记录错误时，新建“更正”条目并引用原 ID。
- 决策发生变化时，新建决策记录，写明替代了哪个决定和新证据。
- 敏感数据不进入台账：不记录 Token、完整轨迹、精确坐标、真实健康描述或其他用户隐私。
- 测试失败也要记录；不能只保留成功结果。

## 7. 工作恢复顺序

每次继续项目时按以下顺序；`index.md`仅在事实归属或链接不清晰时读取：

1. 阅读 `current-status.md`；
2. 阅读当前工作项对应的最近台账记录；
3. 检查工作区实际状态和测试结果；
4. 确认是否有尚未处理的用户反馈；
5. 从“下一步”继续，不重复已验收工作。

## 8. 工作项启动审查与Token控制

每个工作项都必须审查PRD、研发指南和版本路线图，但默认采用“最小充分审查”，而不是全文重读。

### 8.1 固定恢复包

启动时读取：

1. `current-status.md`；
2. 当前工作项最近日志和评审文档；
3. 相关代码、测试和实际工作区状态；
4. PRD中与工作项直接相关的章节；
5. 研发指南中对应的实现/评测章节；
6. 路线图中对应模块行、版本范围和Gate；
7. 最近相关决策记录。

`index.md`只有在事实归属或链接不清晰时读取；已验收且未变化的章节不重复加载。

### 8.2 启动审查卡

编码前只记录以下摘要，不复制主文档全文：

```text
工作项：
PRD依据：
研发指南依据：
路线图依据：
相关决策：
范围：
不做什么：
是否存在实质冲突：
验收标准：
```

### 8.3 全文复查触发条件

以下情况才需要完整复查PRD、研发指南和路线图：进入新的Demo/Alpha/Beta/RC/上线阶段；Agent架构、模型、RAG、Function Calling、隐私、安全或数据边界发生重大变化；用户改变产品方向；发现实质冲突；连续完成3–5个工作项后的阶段巡检；或准备Gate/版本放行。

### 8.4 事实源优先级

- PRD：产品行为、用户体验和业务边界；
- 研发指南：技术实现、Agent、Prompt、工具、Schema、评测和兜底方法；
- 版本路线图：版本范围、优先级、Gate、灰度和回滚；
- 台账：实际完成状态、测试、反馈、验收和下一项；
- 决策日志：用户已确认的取舍，覆盖旧的提议性描述。

文档之间只保留必要摘要和链接，避免把同一规则在多处完整复制。文档治理本身若需重构，应作为独立工作项，不与功能实现混做。
