## 1. 用户目标重新表述

单次骑行详情必须先是一款在无AI时也成立的数据产品：FIT/GPX解析后展示本次骑行的地图/轨迹、概要、图表和详细数据。AI的职责不是评价数据是否完整，也不是复述字段，而是在确定性指标、分段特征和可比历史基础上回答：本次骑得怎么样、表现在哪些维度、相对自己有何变化、有什么亮点和下一步建议。

## 2. 当前实现与PRD的差距

| 范围 | PRD/用户要求 | 当前观察 | 影响 |
|---|---|---|---|
| 无AI概要 | PRD 6.2要求地图/轨迹、日期、距离、时长、速度、爬升、心率、踏频、功率、运动消耗 | 当前仅四项概要卡和聚合数据Tab | B0不等于完整的无AI骑行详情 |
| 图表 | 速度/海拔/心率/功率/踏频曲线与区间 | `RideActivity v0.1`没有轨迹或时序序列合同，解析器只保留聚合指标 | 不能仅通过前端补图，需新增时序合同和解析链路 |
| AI解读 | 多维分析、整体评价、亮点、建议，且不是数据罗列 | 当前输出合同主要是summary+3 highlights；快照只含单次聚合claim | Prompt缺少可用于专业评价的确定性特征 |
| 历史比较 | 近30天、同路线、个人最佳和趋势 | 当前没有历史存储/查询/比较快照 | 模型不能可靠声称进步、排名或趋势 |
| 数据能力 | 按实际可用字段分析，支持功率有/心率无等组合 | 当前互斥L1/L2/L3；有功率即L3并默认可谈心率主题 | 能力表达和硬门会产生误判 |
| 版本规划 | 各PRD模块需有实现阶段、依赖和放行条件 | 现路线图按风险阶段描述范围，但缺少完整模块×版本矩阵 | 容易局部优化偏离PRD主线 |

## 3. 第一性原理职责拆分

| 问题 | 机制 | 原因 |
|---|---|---|
| FIT/GPX解析、地图轨迹、曲线、最大/平均值 | 确定性解析与UI | 原始事实不能由模型生成 |
| 区间分布、分段事件、爬升密度、配速/功率稳定性 | 版本化规则/特征引擎 | 需要可复算、可测试、可引用 |
| 历史记录和精确趋势 | 数据库查询/只读API | 私有、当前、结构化、需权限和精确窗口 |
| 自动骑后分析的历史上下文 | 服务端预取并生成`HistoricalComparisonSnapshot` | 固定工作流不需要让模型自由决定取哪些事实 |
| 对话中按问题读取历史 | 只读Function Calling | 只有部分问题需要，参数与权限可严格定义 |
| 骑行知识、术语、安全说明 | 审核知识库RAG | 答案存在于可检索文档，需来源与更新治理 |
| 整体评价和自然语言解释 | LLM | 负责组织已验证事实关系和用户可理解表达 |

原始FIT/GPX、历史指标和用户档案不得向量化后作为事实源。RAG召回相似记录无法保证骑行ID、时间窗口、最新状态、权限、删除和数值精确性。

## 4. 建议的新数据与Agent分层

1. `RideActivity v0.2`：本次聚合指标、来源、质量。
2. `RideSeries v0.1`：经过隐私与质量处理的轨迹/时间序列，支持地图和曲线，不直接发送给LLM。
3. `RideFeatureSnapshot v0.1`：规则计算的速度/心率/功率/踏频/爬坡/事件特征及证据ID。
4. `HistoricalComparisonSnapshot v0.1`：样本量、窗口、同路线/全部骑行范围、基线、本次变化、可比性和趋势证据。
5. `RideAnalysisContext v0.2`：只把本次允许事实、特征和必要历史对比提供给模型。
6. AI输出：整体评价、多维解读、亮点、建议、限制和证据引用；数据质量仅在异常影响结论时作为限制，不作为主要评价对象。

## 5. 能力模型调整建议

用能力集合取代互斥业务层级：

- `route`、`timing`、`elevation`；
- `heartRate`、`heartRateZones`；
- `power`、`powerZones`、`normalizedPower`、`trainingLoad`；
- `cadence`；
- `historyComparison`、`sameRouteComparison`、`trend`；
- `userProfile`、`verifiedFtp`、`verifiedMaxHeartRate`。

每个分析维度声明必需能力。功率可用但心率缺失时照常分析功率，跳过心率；有踏频就分析踏频。L1/L2/L3可暂留为fixture/测试分组名称，不作为模型事实门和用户标签。

## 6. Few-shot工程建议

- Few-shot需要加入，但不能把大量示例直接堆入System Prompt。
- 建立独立版本化样例库，覆盖：仅轨迹、仅心率、仅功率、心率+功率、首次无历史、历史可比、历史不可比、缺字段和受限修复。
- Demo阶段在Prompt中保留2–3个最小正反例；后续由确定性能力路由选择示例，不使用向量RAG选择数值分析样例。
- 每个示例必须关联输入claim、预期分析维度、禁用结论和质量评分；Prompt变更必须回归相同用例。

## 9. PRD 6.5「AI骑行伙伴对话」专项审计

### 9.1 已一致、无需改变方向的内容

- 产品采用一个用户可见Agent，拆为`ride_analysis_v1`和`ride_chat_v1`两条显式Workflow。
- 用户私有骑行数据通过服务端授权的只读Function Calling读取；RAG只检索经过审核的通用骑行知识，不作为历史数值事实源。
- 服务端负责用户归属、权限、最小上下文、输出Schema与证据校验；模型不直接访问数据库，也不开放写入、删除、发消息等副作用工具。
- 工具失败、模型失败和安全请求均应进入版本化降级链路；对话不应绕过既有安全、隐私和事实边界。

### 9.2 需要逐项确认的冲突或缺漏

1. **产品边界冲突**：6.5写“与骑行无关也正常回答”，与窄域AI骑行伙伴定位及当前System Prompt冲突。
2. **主动读取缺少合同**：初始消息直接展示累计数据、体能评分和趋势，但未定义主动读取的最小字段、首次用户行为和“体能评分”的可信来源。
3. **快捷问题超出准入范围**：路线推荐、膝盖疼、恢复、训练计划和体能评分分别涉及实时外部数据、健康安全、处方型建议或尚未冻结的衍生指标。
4. **历史不足规则过于机械**：不能对所有问题统一提示“记录少于3次”；只有用户主动询问趋势/比较且证据不足时才解释，其他问题仍应正常回答。
5. **旧能力门冲突**：6.5和工具合同仍以L1/L2/L3描述能力，需与`DEC-030`的原子能力集合统一。
6. **设备升级话术不当**：缺数据时不应固定提示连接心率/功率设备，应根据用户问题和实际缺失能力决定是否引导。
7. **医疗与安全边界不完整**：笼统“建议就医”不足以覆盖急症固定分流、非诊断声明和`DEC-036`的非处方边界。
8. **安全提醒可能重复**：“永远推荐佩戴头盔”应改为仅在相关安全场景触发，避免无关回答重复插入。
9. **对话记忆与隐私缺漏**：未定义记忆内容、最小上下文、保留/删除、用户控制、精确位置保护和日志脱敏。
10. **工具合同缺漏**：`get_user_data_capability`返回L1/L2/L3；工具参数、返回上限、超时、错误码、一次重试和跨用户拒绝需冻结。
11. **输出与降级合同缺漏**：6.5未明确对话输出Schema、证据引用、一次受限修复、工具/模型超时和B0确定性降级的用户表现。
12. **版本范围过宽**：6.5把完整对话能力写成统一范围，缺少Demo/Alpha/Beta/MVP的分期、依赖和放行Gate。

以上第2–12项依赖第1项产品边界确定后再逐条确认。确认前不修改PRD正文、System Prompt或Workflow配置。
