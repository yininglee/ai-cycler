# ITEM-V011｜HistoricalComparisonSnapshot历史事实合同评审

> 日期：2026-08-21  
> 状态：`ACCEPTED`  
> 当前阶段：v0.1 证据型Demo / G1「Demo核心价值」  
> 边界：只建立本地/Fixture历史比较事实链，不接入模型、Prompt、扣子、RAG或用户界面。

## 1. 工作项目标

将历史查询和比较从模型职责中移出，固化为版本化的`HistoryQueryService`与`HistoricalComparisonSnapshot v0.1`。服务只返回已经按窗口、路线、测量来源、算法口径、场景、运动类型和数据质量筛选并计算好的结构化事实；后续自动骑后解读和`compare_rides`工具共用这一构建器。

## 2. 依据审计

### 2.1 已核对来源

- PRD 6.3：历史变化必须由确定性比较服务按指标、窗口、路线/设备/场景口径和有效样本判断；不可比时不输出趋势。
- PRD 7.5.3：Snapshot至少包含版本、锚点、窗口、有效样本及纳入口径、本次值/基线值/变化、同路线结果、可比性和claimIds；模型不得重选样本或重算。
- PRD 7.6.1/7.6.2：自动解读由服务端预取Snapshot；对话日后通过只读比较工具复用同一服务，历史数值不使用RAG。
- 版本路线图：v0.1先交付本地/Fixture历史合同，v0.2再做持久化、权限和删除同步，v0.5才验证30天/同路线/同口径趋势正式能力。
- 研发指南与DEC-031/043：首次/不可比自动解读静默省略历史；用户主动询问时才解释不可比原因；不设置“少于3条全局不足”门槛。

### 2.2 冲突结论

未发现需要用户确认的实质冲突。PRD有意要求“版本化规则”但未冻结Demo阶段的具体最小样本和路线算法；本项将`30天窗口、至少2条有效历史样本、可信routeKey同值`作为可替换的`v0.1`技术基线，并将指标可比性规则升级为`metric-comparability-v0.2`，不宣称正式长期趋势能力。

## 3. 冻结的V0.1规则

| 规则 | v0.1基线 | 说明 |
|---|---|---|
| 时间窗口 | 默认30天，输入限制1–365天 | 只纳入锚点之前的历史，排除未来和窗口外记录 |
| 运动口径 | 同一`sport` | 不同运动类型不混入基线 |
| 候选设备/场景 | 默认`any`，可选`same` | 这是候选池筛选，不等于每个指标都必须同设备/同场景 |
| 全部历史 | `routeScope=all` | 只用于同一运动且窗口内的候选 |
| 同路线 | `routeScope=same_route`或Snapshot附带结果 | 只接受权威存储提供的`routeKey`；不存在时`ROUTE_KEY_MISSING`，不使用相对SVG形状猜路线 |
| 有效样本 | 每个指标至少2条有效值 | 不是全局“记录少于3条”门槛；缺指标、低质量值不计入该指标样本 |
| 基线 | 有效历史值算术平均 | 单位必须与锚点一致；基线为0时不生成相对变化 |
| 输出结论 | 直接变化`change`或限定参考变化`reference_change`，不生成长期`trend` | 趋势需后续多窗口/正式规则切片 |

### 3.1 指标可比性矩阵

候选池筛选与指标可比性分为两层。`deviceScope`/`sceneScope`只控制候选池；指标最终按测量来源类别、计算方法和场景敏感性判断，不把“同设备”作为所有指标的统一硬门槛。

| 指标类别 | 跨路线 | 设备 | 场景 | 可用表达 |
|---|---|---|---|---|
| 距离/时间 | 可比 | 任意 | 任意 | 直接变化 |
| 运动消耗 | 可参考 | 同计算方法/来源口径优先，不要求同设备 | 任意 | 参考变化；设备值、公式估算和功率换算不混作同一基线 |
| 平均/最高速度 | 不可直接比较 | 同GPS/计时来源类别且质量可比 | 同场景 | 需同路线，直接变化 |
| 累计爬升/海拔特征 | 不可直接比较 | 同海拔来源类别且质量可比 | 不作硬门槛 | 需同路线，直接变化 |
| 心率均值/峰值/特征 | 可参考 | 同心率传感器类别且质量可比 | 同场景 | 参考变化，不表述为骑行水平提升 |
| 功率/NP/功率特征 | 可参考 | 同功率计/校准来源类别且质量可比 | 同场景 | 参考变化，不表述为路线表现提升 |
| 踏频/踏频特征 | 不可直接比较 | 同踏频来源类别且质量可比 | 不作硬门槛 | 需同路线，直接变化 |

当前版本没有“同路线类型/路线难度”归一化，因此不同路线只能进入候选池，不能用于速度、爬升、踏频和分段表现的强结论。

## 4. Snapshot合同

`HistoricalComparisonSnapshot v0.1`包含：

- `comparisonVersion`、`anchorRideId`；
- `range`：窗口起止、时区、路线/设备/场景范围；
- `inclusionPolicy`：`prior-same-sport-within-window-v0.1`；
- `metricPolicyVersion`：`metric-comparability-v0.2`；
- 候选历史ID及候选数；
- 每个指标的锚点值、基线值、样本量、绝对/相对变化、claim/evidence和逐指标可比性；
- `sameRoute`结果及`routeMatchVersion=route-match-key-v0.1`；
- 稳定原因码：无时间、无候选、指标缺失、样本不足、路线未匹配、运动/设备/来源类别/计算方法/场景不匹配、基线为0、锚点非法等。

Snapshot不返回原始FIT/GPX、完整轨迹、精确坐标或用户无权访问的记录；模型只能解释Snapshot，不得重选样本、改变窗口、重算变化率或把不可比改写成趋势。

## 5. 验收标准

- 同一输入和规则版本重复查询结果稳定；
- 30天窗口、未来/过期记录、运动类型、设备/场景和路线筛选可测试；
- 每个指标分别统计有效样本，至少2条才可比；不可比没有趋势claim；
- 首次骑行或无可比历史返回结构化不可比原因，自动流程可静默省略；
- 同路线只依赖可信routeKey，不从隐私安全的相对SVG轨迹反推路线身份；
- Snapshot含窗口、纳入口径、同路线判定版本和claim/evidence；合同校验拒绝版本、样本、数值和claim错误；
- 不接入模型、RAG、Function Calling、真实数据库或UI。

## 8. 用户预览反馈与修订

用户确认将矩阵调整为“测量来源/算法口径/质量/场景敏感性”规则：距离/时间可跨路线直接比较；运动消耗按计算方法和来源口径比较，不强制同设备；心率和功率需要同类传感器/校准来源并按场景限定为参考变化；速度需要同类GPS/计时来源和同场景；海拔与踏频放宽同场景硬门槛但仍要求同路线、同类来源和质量可比；不同路线不会被统一判定为全部不可比，也不会被模型自行放宽。
