# AI 骑行伙伴：数据处理与原子能力学习笔记

> 记录日期：2026-08-22  
> 主题：从 FIT/GPX 到 AI 骑后解读，理解数据分层、原子能力、Claim、展示值和模型边界

## 1. 结论先行

AI 骑后解读不是“把 FIT/GPX 文件直接交给大模型”，而是一条确定性数据管道：

```text
FIT / GPX
  ↓
解析与标准化
  ↓
RideActivity + RideSeries
  ↓
质量校验与能力判断
  ↓
RideFeatureSnapshot
  ↓
HistoricalComparisonSnapshot
  ↓
RideAnalysisContext
  ↓
AnalysisEligibility
  ↓
大模型解释
  ↓
服务端校验、修复或 B0 兜底
  ↓
页面展示
```

核心分工是：

- 规则和代码负责确定“事实是什么”；
- 原子能力合同负责确定“哪些能力可以使用”；
- Claim 负责确定“模型可以引用哪些证据”；
- 大模型负责把事实解释成用户能理解的语言；
- 服务端负责阻止越权、幻觉和不安全表达。

## 2. 从文件到统一数据

### 2.1 解析层

FIT 和 GPX 首先被转换成统一的数据合同：

- `RideActivity`：骑行概要、指标、来源和质量信息；
- `RideSeries`：路线、海拔、速度、心率、功率、踏频等序列。

不同文件格式的字段名称可能不同，但进入业务层后应使用统一字段，例如：

```text
distanceM
movingTimeS
elevationGainM
avgSpeedMps
avgHeartRateBpm
avgPowerW
avgCadenceRpm
```

### 2.2 质量和标准化层

服务端在指标进入 AI 之前检查：

- 字段是否存在；
- 单位是否正确；
- 时间戳是否可靠；
- GPS 是否存在异常跳点；
- 传感器覆盖率是否足够；
- 计算指标是否带公式版本；
- 文件是否损坏或不是骑行记录。

例如，没有时间戳的 GPX 可以保留路线、距离和海拔，但不能伪造骑行时间和平均速度。没有可靠功率时，不能因为文件属于某个等级就开放功率分析。

## 3. 原子能力合同在哪一层

原子能力合同位于“确定性能力判断层”，在特征计算和 AI 调用之前：

```text
RideActivity + RideSeries
  ↓
AtomicCapabilityProfile
  ↓
RideFeatureSnapshot
  ↓
RideAnalysisContext
  ↓
AnalysisEligibility
```

它回答的是：

> 当前记录能否安全支持某种分析？

它不回答具体数值是多少。

### 3.1 原子能力示例

```json
{
  "key": "speed",
  "available": true,
  "sources": ["ride_activity", "ride_series"],
  "qualityStatus": "valid",
  "dependencyKeys": ["timing"],
  "evidenceIds": ["EV-SL1-004"]
}
```

```json
{
  "key": "heartRateZones",
  "available": false,
  "dependencyKeys": ["heartRate", "maxHeartRateBaseline"],
  "unavailableReason": "DEPENDENCY_UNAVAILABLE"
}
```

### 3.2 能力和数据不能画等号

```text
有功率数据
  ≠ 可以分析训练负荷

有功率数据 + 可信 FTP + 训练负荷规则
  = 才能开放 trainingLoad 能力
```

同理：

- 有心率数据，不代表一定能生成心率区间；
- 有速度数据，不代表一定能分析速度趋势；
- 有历史记录，不代表这些记录一定可比；
- 有海拔数据，不代表可以直接评价路线平缓或陡峭。

### 3.3 当前原子能力类别

```text
route、distance、timing、speed、elevation
heartRate、maxHeartRateBaseline、heartRateZones
power、normalizedPower、verifiedFtp、powerZones、trainingLoad
cadence、userProfile
historyComparison、sameRouteComparison、trend
```

原子能力由字段、质量、依赖、用户资料、历史可比性和已实现规则共同决定，不再用 L1/L2/L3 作为 AI 分析门。

## 4. 特征层：事实特征不等于评价

`RideFeatureSnapshot` 是服务端根据时序数据计算出的版本化事实，例如：

- 速度均值；
- 速度标准差；
- 速度变异系数；
- 首段四分之一和末段四分之一的差值；
- 海拔最小值、最大值和落差；
- 心率、功率、踏频的类似统计。

每个特征都应带：

- `claimId`；
- `evidenceIds`；
- `formulaVersion`；
- 数据质量和置信度。

### 4.1 统计量不自动产生自然语言结论

以下转换不能由模型自行完成：

```text
变异系数 → “节奏稳定”
标准差较小 → “波动不大”
累计爬升 → “路线平缓”
25 公里 → “长距离”
首末四分之一差值 → “后半程下降”
```

只有当规则层提供了版本化阈值或分类 Claim 时，模型才可以使用对应评价。否则模型只能忠实描述事实，例如：

```text
首段与末段四分之一的平均速度存在差异。
```

## 5. Claim：模型可引用的证据白名单

`RideAnalysisContext` 会把允许模型引用的事实放进 `allowedClaims`：

```json
{
  "claimId": "claim:ride-l1-built-in-sample:distanceM",
  "kind": "metric",
  "key": "distanceM",
  "value": 25000,
  "unit": "m",
  "confidence": "high",
  "evidenceIds": ["EV-SL1-001"]
}
```

模型输出中的每一个 Claim ID 都必须来自这个白名单。服务端还要校验文案中的数字是否来自对应 Claim，防止模型凭空生成数据。

## 6. 原始值、标准值和展示值

“原始值”需要区分两个概念：

1. 文件中的原始字段，例如 FIT 文件里的原始整数或厂商字段；
2. 服务端标准化后的内部值，例如 `25000 m`。

AI 上下文通常不应继续传文件原始结构，而是传第二种标准化值。

### 6.1 为什么需要展示值

当前上下文可能只提供：

```json
{
  "value": 25000,
  "unit": "m"
}
```

模型看到后自行写成“25 km”。数学上可能正确，但这违反“模型不负责计算和单位换算”的原则，也会让页面、AI 和历史比较各自使用不同换算逻辑。

更稳妥的结构是由服务端提前提供：

```json
{
  "key": "distanceM",
  "value": 25000,
  "unit": "m",
  "displayValue": 25,
  "displayUnit": "km",
  "displayFormulaVersion": "metric-display-v0.1"
}
```

含义：

- `value + unit`：内部计算、排序、历史比较和审计；
- `displayValue + displayUnit`：页面和 AI 文案使用；
- `displayFormulaVersion`：追溯展示换算规则。

模型只能引用服务端给出的展示值，不能自行把米换成公里、秒换成小时或 m/s 换成 km/h。

### 6.2 这不是重复存储业务事实

展示值不是另一份独立事实，而是同一事实的确定性用户表达：

```text
25000 m = 25 km
3600 s = 1 h
6.9444 m/s = 25 km/h
```

换算规则由代码维护，模型只做语言组织。

### 6.3 当前状态

当前代码合同已经有标准化 `value/unit` 和 `allowedClaims`，但展示值字段尚未正式加入 `RideAnalysisContext v0.2`。因此“增加展示值”属于待确认的合同调整，不是已经完成的实现。

## 7. RideAnalysisContext 的职责

它是送入骑后 AI 的最小、受控上下文，主要包括：

- `capabilities`：原子能力；
- `recordedMetrics`：记录值；
- `derivedMetrics`：计算值；
- `estimatedMetrics`：估算值；
- `featureSnapshot`：特征事实；
- `historicalComparison`：历史比较快照；
- `profileFacts`：明确请求的个人资料白名单；
- `allowedClaims`：允许引用的 Claim；
- `forbiddenClaims`：禁止涉及的主题；
- `limitations`：真实边界；
- `safetyFlags` 和 `privacyFlags`。

原始轨迹、精确坐标、文件名和不可信自由文本不直接送给模型。

## 8. AnalysisEligibility 的职责

`AnalysisEligibility` 在模型调用前读取上下文，决定：

- 是否允许调用模型；
- 允许哪些分析维度；
- 必须引用哪些 Claim；
- 是进入 B2 还是 B0；
- 是否触发安全停止。

例如 L1 当前只有速度和海拔特征：

```json
{
  "eligible": true,
  "allowedDimensionKeys": ["pace", "climbing"],
  "fallback": "b0"
}
```

模型不能因为提示词写得更积极，就自行开放心率、功率或历史趋势。

## 9. 大模型在链路中的正确职责

大模型适合做：

- 把确定性事实翻译成自然语言；
- 组织整体评价；
- 从已开放维度中选择有认知增量的内容；
- 生成低风险、可执行的建议；
- 生成分享文案。

大模型不适合做：

- 从原始文件计算指标；
- 单位换算；
- 判断数据是否可比；
- 选择历史样本；
- 决定是否开放心率、功率或训练负荷；
- 自行定义长距离、轻松、稳定、路线平缓等阈值；
- 进行医疗诊断或训练处方。

## 10. 服务端输出校验和兜底

模型输出后，服务端校验：

- JSON 和 Schema；
- Claim ID 是否存在；
- 数字是否在允许范围；
- 维度是否被 `AnalysisEligibility` 开放；
- 首次骑行是否错误展示历史不足；
- 是否出现无依据的体感、强度、路线和训练评价；
- 是否违反安全规则。

失败处理：

```text
首次模型输出
  ↓ 失败
一次受限修复：只修结构、Claim、数字和越权表达
  ↓ 再失败 / 超时 / 供应商错误
B0 确定性模板
```

修复调用不能让模型新增事实，也不能借机重新生成一套分析。

## 11. 本次 L1 冒烟的学习点

本次扣子输出的结构是成功的，但语义质量失败，暴露了几个典型问题：

- 25 公里被归类成“长距离”；
- 无心率、功率和主观体感时被评价为“轻松、舒适、休闲”；
- 统计特征被直接改写为“稳定、波动不大”；
- 首末四分之一被改写成“前后半程”；
- 海拔被改写成“路线平缓”；
- 首次骑行向用户展示“没有历史骑行数据”。

这说明：

> JSON 合法、Claim 存在、维度正确，不等于 AI 解读具有产品价值。

还必须进行语义边界评测和用户价值评测。

## 12. 产品经理的设计方法

面对任何一个 AI 分析需求，可以依次问：

1. 这是事实、计算结论、通用知识还是自然语言表达？
2. 事实是否应由数据库和规则层提供？
3. 是否需要原子能力和依赖条件？
4. 该结论是否需要版本化阈值？
5. 模型需要引用哪个 Claim？
6. 用户看到的是内部标准值还是展示值？
7. 如果没有足够证据，是删掉该维度、返回 `null`，还是降级 B0？
8. 输出后如何自动校验？
9. 失败后最多修复几次？
10. 如何用固定评测集证明这次修改真的变好了？

## 13. 一句话记忆

```text
能力决定能不能说，特征决定有什么事实，Claim 决定凭什么说，
展示值决定怎么给用户看，模型决定怎么解释，服务端决定哪些话不能出现。
```

## 14. 学习补充：事实如何映射为解释（2026-08-22）

### 14.1 核心问题

如果规则层已经限制了大模型不能自行定义“长距离、轻松、稳定、路线平缓”等结论，大模型是否只剩下平铺数据？

答案是否定的。大模型仍然负责把已验证事实组织成用户能理解、有认知增量的解释；规则层只负责限定每项事实最多能够支持到哪一级结论。

例如，已验证事实是：

```text
末段四分之一平均速度低于首段四分之一。
```

模型可以解释为：

```text
本次骑行首段与末段四分之一的速度存在差异，末段速度较低，
说明两段骑行节奏不同；下次可以结合当时体感继续观察末段变化。
```

但当前不能直接解释为：

```text
你的后半程体能下降，符合长距离骑行的疲劳规律。
```

原因是“前后半程”“体能下降”“长距离”和“疲劳规律”都不是现有 Claim 能直接证明的事实。

** “当前 L1 确实会暂时偏向“事实 + 事实之间的关系描述”，但不是只能平铺数据。真正有价值的丰富解释，需要补充版本化特征和解释规则。” **

### 14.2 模型与规则的正确分工

| 层级 | 负责内容 | 示例 |
| --- | --- | --- |
| 数据与规则层 | 事实、计算、阈值、分类和可比性 | 首末四分之一速度差、心率区间、同路线历史变化 |
| Claim 合同 | 声明模型可以引用什么、依据是什么 | `speedFirstLastDeltaMps`及其证据和公式版本 |
| 大模型 | 选择重点、组织关系、解释意义、生成自然语言 | 将首末段差异解释为“本次骑行末段节奏发生变化” |
| 服务端校验 | 阻止模型越过事实边界 | 拒绝“体能下降”“长距离”“后半程”等无依据表达 |

规则不是替代模型，而是给模型提供“解释护栏”和可靠语义积木。

## 15. 从事实到骑行表现解释的四层结构

### 15.1 第一层：确定性事实

包括距离、时间、平均速度、累计爬升、心率、功率、NP、踏频、运动消耗，以及各指标的数据质量和来源。

这层不需要大模型判断真伪，大模型只负责选择和表达。

### 15.2 第二层：关系特征

这层描述事实之间的关系，例如：

- 首段与末段四分之一的速度差；
- 心率首末变化；
- 功率变异系数；
- NP 与平均功率的关系；
- 踏频与速度或功率的关系；
- 累计爬升与距离的关系；
- 本次指标与可比历史基线的差异。

关系特征可以支持“发生了什么变化”，但不一定能支持“表现好不好”。

### 15.3 第三层：分类 Claim

只有规则层定义并校准阈值后，才能生成“稳定、波动较大、平缓、强度较高”等分类。

分类 Claim 应至少包含：

```text
claimId
分类名称和值
输入 Claim IDs
公式或阈值版本
适用场景
置信度
允许表达
禁止表达
```

例如：

```json
{
  "claimId": "claim:ride-xxx:classification:speedVariabilityLow",
  "kind": "classification",
  "key": "speedVariability",
  "value": "low",
  "basedOnClaimIds": [
    "claim:ride-xxx:feature:speedCoefficientOfVariation"
  ],
  "ruleVersion": "speed-interpretation-v0.1",
  "allowedLanguage": ["速度变化相对集中"],
  "forbiddenLanguage": ["骑行水平较高", "体能很好", "骑行很轻松"]
}
```

### 15.4 第四层：骑行水平和长期趋势

单次骑行可以解释本次节奏、输出和负荷，但通常不能判断用户整体骑行水平。

要判断“是否进步、耐力是否增强、当前水平如何”，至少需要：

- 多次历史记录；
- 可比路线、场景、测量来源和计算方法；
- 个人资料或训练基线；
- 版本化趋势规则；
- 最小样本量和变化显著性要求。

因此，单次骑行表现和用户长期骑行水平必须分开设计和评测。

## 16. 后续规则建设范围

需要逐步补充的规则包括：

| 维度 | 关系特征或规则候选 |
| --- | --- |
| 速度 | 首末四分之一差、前后半程差、速度变异、停车影响、历史同路线变化 |
| 心率 | 最大心率基线、心率区间、时间分布、首末变化、心率漂移及适用条件 |
| 功率 | 功率变异、NP/平均功率、FTP区间、IF/TSS及其质量门 |
| 踏频 | 均值、分布、变异、与速度/功率关系；不设脱离场景的统一优秀值 |
| 海拔 | 海拔范围、爬升密度、坡度、爬升段识别、路线起伏分类 |
| 历史 | 指标级可比性、时间窗口、最小样本、变化类型和趋势显著性 |
| 运动消耗 | 同计算方法和来源口径下的历史比较 |
| 建议 | 证据支持范围、低风险通用建议和高风险禁止项 |

这些规则不应一次性全部实现。应按照真实用户价值和错误风险排序，先实现能明显提高骑后解读价值、且容易获得可靠证据的关系特征。

## 17. L1 首次冒烟的准确率应如何评价

不能用一个总百分比概括这次输出，因为结构正确和语义正确是不同问题。

| 评测层 | 本次结果 |
| --- | --- |
| JSON结构、根字段和类型 | 通过 |
| Claim ID 是否来自白名单 | 通过 |
| 距离、爬升等直接事实 | 基本通过 |
| 首末四分之一特征语义 | 失败，被改写为前后半程 |
| 长距离、轻松、舒适、休闲分类 | 失败，没有规则或证据 |
| 路线平缓分类 | 失败，没有版本化路线规则 |
| “符合体能变化规律”因果解释 | 失败，没有生理或历史证据 |
| 首次骑行历史静默 | 失败，错误展示历史不足 |

因此，本次结论是：

> 结构准确性通过，Claim 引用准确性通过，直接事实部分基本通过，但解释语义准确性不通过。

后续基准测试应至少分开记录：

1. 硬事实正确率；
2. Claim 引用正确率；
3. 特征语义正确率；
4. 无依据分类和因果越界率；
5. 用户价值评分；
6. 安全与隐私违规率。

## 18. 为什么模型会产生这些错误

无 Few-shot 的通用大模型会根据预训练中的语言习惯补全解释：

- 将 25 公里按常识归类为“长距离”；
- 将无心率和功率错误理解成低强度，从而生成“轻松、休闲”；
- 将 260 米爬升和 41.6 米海拔范围按常识归类为“路线平缓”；
- 将负的首末四分之一速度差改写为“后半程变慢”；
- 再用“符合体能变化规律”为变化补充一个听起来合理的因果解释。

这些内容读起来流畅，但不等于有证据。

提高准确率不能只靠一种手段，而应组合使用：

```text
修正输入数据与样例口径
  + 确定性特征和分类 Claim
  + 收窄 Prompt 的语义边界
  + 输出合同和服务端校验
  + 最多一次受限修复
  + B0 兜底
  + 经人工评审的 Few-shot 对照实验
```

其中：

- 规则解决“什么结论成立”；
- Prompt 解决“模型如何使用和表达这些结论”；
- 校验器解决“错误输出是否允许展示”；
- 评测解决“修改后是否真的更准确、更有价值”。

## 19. 本次确认的工程决策

### 19.1 修正 L1 内置样例速度口径

原样例存在：

- 概要平均速度为 25 km/h；
- 速度序列平均值为 22 km/h。

这会让概要和序列特征互相矛盾。现已确定以概要 25 km/h 为准，使速度序列均值与概要一致。

### 19.2 首版严格使用首末四分之一

当前特征计算的是：

```text
末段四分之一均值 - 首段四分之一均值
```

因此模型只能说“首段与末段四分之一”，不能改写成“前半程与后半程”。未来如果确有产品价值，再新增独立的前后半程特征。

### 19.3 服务端提供确定性展示值

`allowedClaims`保留内部标准值和原始单位，同时增加服务端生成的用户展示值：

```json
{
  "value": 25000,
  "unit": "m",
  "displayValue": "25",
  "displayUnit": "km",
  "displayFormulaVersion": "metric-display-v0.1"
}
```

这样做的目的不是限制大模型表达，而是避免让模型负责单位换算和数字计算。模型直接使用展示值，再负责解释和组织语言。

## 20. 本轮学习结论

```text
大模型负责把事实变成解释，但不能把常识变成用户事实。
规则定义事实能支持到哪里，Prompt指导如何表达，校验器决定错误能否展示。
```

## 21. 版本化规则与分类 Claim（2026-08-22）

### 21.1 什么是版本化规则

版本化规则是指：将会影响数据计算、能力判断、指标比较、分类结果或输出放行的规则，作为有明确版本号、可追溯、可复现、可回滚的独立合同管理。

规则至少应记录：输入字段、计算公式、阈值、适用范围、最小数据量、数据质量要求、无法判断时的处理、反例、评测结果和生效版本。

例如“速度波动较小”不能只写成一句Prompt要求，而应先定义：

```text
ruleId: speed-variation-classification
ruleVersion: v1.0
输入: 有效速度序列
公式: CV = 标准差 / 平均速度
数据门: 有效样本数和覆盖率满足要求
阈值: 由离线基准确定
无法满足: 不生成分类Claim
```

服务端依据规则生成分类Claim，大模型只负责表达，不能自行把标准差解释成“稳定”或“波动小”。

### 21.2 当前已经存在的版本化规则/合同

| 领域 | 当前版本 | 作用 |
| --- | --- | --- |
| FIT解析 | `FIT parser v0.2` | 提取FIT活动、传感器和轨迹 |
| GPX解析 | `GPX parser v0.3` | 提取GPX路线、距离、海拔和时间 |
| GPS质量 | `GPS quality v0.1` | 识别跳点、异常速度和异常轨迹 |
| 活动数据 | `RideActivity v0.2` | 统一基础骑行事实 |
| 时序数据 | `RideSeries v0.1` | 统一速度、心率、功率、踏频、海拔序列 |
| 用户资料 | `UserProfile v0.1` | 管理年龄、身高、体重、最大心率、FTP |
| 原子能力 | `AtomicCapability v0.1` | 判断单项数据能力是否可用 |
| 骑行特征 | `RideFeatureSnapshot v0.1` | 计算均值、标准差、变异系数、首末差值 |
| 历史比较 | `HistoricalComparisonSnapshot v0.1` | 生成历史比较事实 |
| 可比性 | `metric-comparability v0.2` | 按指标、来源、方法、质量和场景判断可比性 |
| AI上下文 | `RideAnalysisContext v0.2` | 形成模型可见事实白名单 |
| AI准入 | `AnalysisEligibility v0.1` | 控制是否调用模型和允许维度 |
| AI输出 | `ride-analysis-output-v0.3` | 约束输出字段、Claim、建议和安全等级 |

首版首末速度特征固定使用“首段四分之一 vs 末段四分之一”。该口径属于当前特征计算合同，未独立建立前半程/后半程规则。

### 21.3 当前尚未建立的分类规则

目前还没有正式的版本化规则支持以下分类：

- 速度波动小/中/大；
- 配速稳定/不稳定；
- 路线平缓/起伏/爬坡型；
- 运动强度低/中/高；
- 疲劳、耐力或后程衰减等级；
- 历史趋势提升/下降/无明显变化。

因此，当前可输出“结束阶段速度低于开始阶段”，但不能从原始差值或海拔范围自行推导“速度稳定”“路线起伏不大”等分类。

### 21.4 没有意义时允许事实降级

事实到意义的解释是模型的价值增强项，不是每个维度的硬性要求。

当没有直接、清晰且对用户有帮助的Claim支持时，合格输出可以是：

> 平均速度25km/h，结束阶段速度比开始阶段低4.49km/h。

也可以省略该维度。最低放行标准是：事实正确、Claim可追溯、不越权、不添加未经支持的程度或因果判断。

### 21.5 什么时候新增分类 Claim

分类Claim不应为了让文案更像AI而增加。只有同时满足以下条件，才进入独立版本化变更：

1. 原始特征在不同文件格式、设备和数据质量下稳定；
2. 用户对该判断有反复、明确的需求；
3. 公式、阈值、适用范围和最小数据门明确；
4. 有无法判断状态和反例处理；
5. 离线基准证明分类比事实罗列更有价值；
6. 完成Claim合同、服务端确定性计算、Prompt边界、校验器和回滚方案。

优先级可按以下顺序评估：配速变化分类、速度波动分类、爬升负荷分类、心率/功率强度分类、历史趋势分类。所有分类都由服务端计算，模型只负责用户语言表达。

### 21.6 本轮结论

```text
基础数据规则先版本化，分类规则后验证再版本化。
没有安全意义时，准确事实罗列优于臆造解释。
规则定义事实能支持到哪里，Prompt指导如何表达，校验器决定错误能否展示。
```
