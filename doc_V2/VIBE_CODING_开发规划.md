## 1. 重构价值闭环

用户导入 FIT/GPX 后，先从标准化骑行记录查看来源清楚、符合字段质量规则的详情事实；需要解释时再请求 AI；AI 不可用时事实页仍完整可用。

## 2. 工作约定

- `RIDE-REF-01` 已于 2026-10-02 验收完成。用户已明确验收 AI 解读业务规则、PRD、技术方案及详情页第 8 节，`RIDE-AI-CONTEXT-01` 四文档设计任务已完成；实现切片仍逐项独立验收。
- 本专项与 V1 业务里程碑并行，不改变 M1-M4 的完成数；不自动推进此前 `CHAT-17` 的验收或后续 AI 解读优化任务。
- 任务状态仅使用 `Backlog / Ready / In Progress / Review / Blocked / Done / Paused`。最多保留一个主要 `In Progress` 或 `Review` 任务。
- 每次开发按“读需求与账本 → 明确范围 → 最小实现 → 自动验证 → 本地预览 → 记录结果 → 用户验收”进行。
- 自检完成进入 `Review` 并停止后续计划工作；只有用户明确通过才能记为 `Done`。
- 每个实现工作项的面向用户验收汇报写在本规划的对应工作项下；《开发进度》保留事实账本、验证、状态及用户验收后的 Done 记录，不再重复放置验收汇报。

- **本项重构**：新增一个独立的"个人资料 + 历史"档案层。每次解读时，系统先登记一份带更新时间的用户资料（年龄、体重、最大心率、FTP，只使用授权的这四项）；再自动查询历史骑行并判断是否可比：够格就自动生成"本次 vs 历史"的证据并放进"相对过去"问题包；没有历史或样本不足就整块关闭，只留下原因。全程没有"是否使用历史"的开关。
- **可核对样例**：
  1. 本次骑行均速 28.8 km/h，用户资料为 35 岁、70 kg、FTP 240 W，**没有任何历史**：四项资料正常登记，"相对过去"明确显示"无历史"，不会出现任何"比以前快/慢"的说法；长期负荷和恢复同样标记"无历史、不可用"。
  2. 同一次骑行，加上两次历史（10 月 1 日均速 21.6 km/h、9 月 28 日均速 18.0 km/h）：系统**自动**生成"本次均速相对历史基线"的历史证据并进入"相对过去"包，用户无需做任何选择；但"长期负荷"和"恢复"仍显示"窗口规则未实现"——即只允许说"比前两次快"，不允许说"近一个月负荷上升、恢复良好"。
  3. 只提供**一条**历史（10 月 1 日 21.6 km/h）：样本不足，历史比较整体关闭，连"比上次快"也不生成，只留下"历史样本不足"的原因。
  4. 把**另一条骑行**的历史档案错传进来：系统直接拒绝并报"骑行不匹配"，绝不把别的骑行的数据混进本次解读。
- **长期负荷与恢复边界**：即使历史比较成功，长期负荷和恢复也只保留"规则未实现"的限制，不生成趋势、恢复完成、过度训练或因果结论；具体的统计窗口和文案由后续任务单独冻结后再开放。

#### `RIDE-AI-S3-02` 验收汇报（已通过）

## 5. 每项任务的验收证据

1. **需求**：PRD 任务范围、非目标及验收条件明确。
2. **自动验证**：相关单元/集成测试、类型检查和生产构建结果写入账本。
3. **预览**：界面任务给本地 URL 和场景路由；文档任务给可点击文件路径及变更摘要。
4. **用户检查**：在本规划对应工作项下提供面向非技术用户的验收汇报和不超过 5 项具体检查点。
5. **关闭**：明确用户确认后，才在进度账本增加一次 Done 记录。
