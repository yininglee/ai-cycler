# AI 解读分析上下文业务规则说明

> 文档定位：V2 重构目标规则，产品经理视角。
>
> 状态：`Review`。本文件定义目标业务合同；代码尚未按本文件完成迁移。
>
> 关联文档：[AI 解读证据体系与上下文重构 PRD](AI解读证据体系与上下文重构_PRD.md)、[开发进度](开发进度.md)、[骑行数据导入与详情页产品规则说明](骑行数据导入与详情页产品规则说明.md)、[V1 事实性 NO-GO 根因分析](../doc_V1/T002-V04-事实性NO-GO根因分析.md)。

## 1. 文档目的

本文件定义一次骑行请求 AI 解读时，系统如何把标准化骑行记录、确定性分析、用户 Profile、合格历史数据和运动科学知识组织成可追溯、可验证、可受限表达的分析上下文，并约束模型调用、Prompt、输出校验和修复。

本次 V2 重构的核心结论是：**不能让一个窄化的“解读计划”层级成为证据白名单。** 所有与某个分析问题相关、通过质量门且可回溯的证据，都必须保留在该问题的完整证据包中；系统仍然可以做资格判断、优先级排序、安全限制和展示编排，但不能用首个匹配 Claim 代替完整证据集合。

本文件解决以下问题：

- 单次骑行要回答哪些分析问题；

- 每个问题需要哪些必需证据、可选证据、时间序列特征和质量门；

- 详情页确定性规则、时序特征、原子能力和原子 Claim 如何衔接；

- 历史数据何时自动进入，并如何解释长期负荷与恢复；

- FTP、NP、IF、TSS、心率基线、体重等 Profile 依赖如何约束结论；

- 运动科学、骑行数据标准和运动科学知识库如何作为独立知识证据进入；

- 哪些数据可以进入 AI，哪些只能记录为不可用或限制；

- 如何防止“稳定、能力提升、恢复良好、符合计划”等无证据结论。

- 如何直连模型 API、约束 Prompt 与结构化输出，并在输出不合格时决定修复或降级。

本文件不定义 FIT/GPX 的底层解析字段，也不把模型生成文本当作事实。导入字段和详情页规则以《骑行数据导入与详情页产品规则说明》为准。

## 2. 产品结论

### 2.1 上下文不是原始文件副本，也不是详情页字段的简单复制

详情页与 AI 都消费同一条标准化 `RideRecord`，但组织目的不同：

| 消费方    | 目标                | 组织方式                   |
| ------ | ----------------- | ---------------------- |
| 详情页    | 展示可核对的事实、图表和确定性分析 | 按摘要、分析、数据模块组织          |
| AI 上下文 | 支持一个或多个明确分析问题     | 按来源、能力、质量、证据包和限制组织     |
| AI 输出  | 向用户表达洞察、相对变化和建议   | 只能引用上下文允许的 Claim 与知识证据 |

上下文应覆盖所有**可用且与问题相关**的数据，不等于把所有原始点、内部中间状态或无关字段直接塞入提示词。

### 2.2 取消 L6 作为窄证据白名单，保留编排职责

历史实现中的“L6 解读计划”只为每个维度取第一条 `fact/performance/capability_evidence`，然后由 L7 裁剪未被选中的 Claim。这种结构导致 L5 已经算出的方差、前后段变化、峰值、功体比等证据丢失，并使模型在缺少波动证据时仍然生成“稳定/平稳”等判断。

V2 将 L6 的职责改为“分析编排与覆盖检查”：

- 识别本次可回答的分析问题；

- 为每个问题生成完整证据包引用范围；

- 计算优先级、展示顺序、必要限制和禁止结论；

- 记录证据覆盖缺口；

- 不删除已通过质量门、且属于该问题的证据。

L7 不再把 `allowedClaims` 重写成“被首个候选引用的 Claim 子集”。它将完整问题包组装成版本化模型输入，并校验完整性、来源、授权和隐私；只排除原始轨迹、精确坐标、文件名等禁止输入，不因展示重点或篇幅删除合格 Claim。模型生成后的事实性与表达校验由独立输出校验负责。

### 2.3 单次骑行的默认分析问题

单次骑行默认覆盖以下问题；实际只对满足质量门的维度生成深入解读：

1. 配速执行：速度、移动时间、停歇和阶段变化是否支持对节奏执行的判断；
2. 爬坡表现：代表性爬坡、爬升、坡度、速度、心率和功率响应如何；
3. 心率负荷：心率水平、区间分布、漂移或前后段变化能说明什么；
4. 功率输出：平均功率、NP、波动、稳定性、峰值和功体比如何；
5. 骑行强度与训练负荷：在用户确认 FTP 可用时，解释 FTP、NP、IF、TSS 之间的关系；
6. 踏频策略：踏频水平、分布、变化及其与速度、功率的关系；
7. 跨传感器配合：速度、心率、功率、踏频、海拔在同一时间或区段的关系；
8. 相对过去的表现：有合格可比历史时自动比较本次与历史；
9. 长期负荷与恢复：PMC 统计窗口（CTL/ATL/TSB）达标时自动解释长期负荷水平与负荷平衡信号。

其中第 8、9 项不是用户开关。**第 8 项：有可用且可比的历史数据就默认使用；没有则省略该部分或明确说明没有足够历史证据，不得由模型自行推断长期趋势。第 9 项（2026-10-06 用户决策）：长期负荷与恢复单独成包，准入即 10.3 节的 PMC 三道门（确认 FTP、满 42 个自然日、满 10 个负荷日），不依赖是否存在可比单次骑行——历史满 42 天但无可比骑行时仍可生成该包。**

### 2.4 用户可见输出结构

AI 输出固定围绕以下结构组织：

- 一句话标签；

- 整体评价；

- 当前骑行高光表现；

- 各维度深入解读；

- 相对过去的表现（有合格可比历史时自动出现）；

- 长期负荷与恢复（PMC 窗口门通过时自动出现）；

- 建议。

“高光表现”和“一句话标签”只能引用已进入证据包的事实或关系 Claim；“建议”必须说明触发它的骑行或历史证据、适用条件与不确定性；引用知识时还须说明知识依据，不能把通用训练知识伪装成用户本次数据结论。

## 3. 上下文输入范围

### 3.1 必须输入

- 与请求 `rideId` 匹配的标准化 `RideRecord`；

- `activity` 和 `series` 的完整结构、字段来源和质量元数据；

- 当前详情页可复用的确定性分析结果及规则版本；

- 当前上下文 Schema、特征、能力和 Claim 规则版本。

### 3.2 条件输入

- Profile 快照：年龄、身高、体重、最大心率、FTP 及其来源、信任状态、更新时间；

- 历史骑行快照：已完成可比性判断的骑行、基线、锚点、范围、证据和比较规则版本；

- 知识证据：经过检索、版本锁定和适用性判断的骑行运动科学、骑行数据标准、运动科学内容；

- 安全与隐私标记：禁止的主题、敏感字段排除、停止生成条件。

条件输入不能因为详情页显示了对应字段就自动视为已经进入 AI；调用方必须显式传入并通过上下文校验。

### 3.3 默认排除

- 原始轨迹点和精确经纬度；

- 上传文件名、未受信任自由文本和无法验证来源的外部数据；

- 解析器未映射且没有标准化定义的 FIT developer fields；

- 规则内部中间状态，除非它被转成带规则版本和证据的可解释 Claim；

- 与当前分析问题无关的用户个人资料。

## 4. 上下文构建总流程

本节对应 PRD 第 4.3 节“重构后的骑行解读工作流”：PRD 说明用户可理解的端到端产品流程，本文件在同一流程上定义输入、证据、能力、Claim、EvidencePacket 和校验合同。详情页第 8 节与技术方案分别承接数据消费边界和模块迁移顺序。

```text
RideRecord + Profile snapshot + historical snapshots + knowledge retrieval
  -> record/activity/series validation
  -> source inventory and quality normalization
  -> time-aligned feature and event extraction
  -> deterministic analysis summaries
  -> complete atomic capability profile
  -> atomic metric/feature/advanced/history Claims
  -> analysis-question coverage matrix
  -> one complete EvidencePacket per eligible question
  -> history auto-inclusion and long-term load/recovery limits
  -> safety, privacy, dependency and unsupported-claim constraints
  -> RideAnalysisContext validation
  -> context assembly and input-boundary validation by complete packet
  -> versioned Prompt and direct model API generation
  -> independent factual and expression validation of model output
  -> bounded deterministic repair / eligible one-time model repair and revalidation
  -> validated output or existing fallback contract
```

这里的 `RideRecord` 只指 `{ activity, series }` 标准化输入，不包含 `TimingSummary`、`ElevationSummary`、`RouteShapeSummary`、`EventClimbSummary`、`ZoneDistribution` 或 `PowerSummary`。这些对象在“deterministic analysis summaries”步骤由规则运行时生成，再按证据合同转换为 Claim、能力、质量或限制。

上下文构建、输入组装与校验、模型生成、输出校验与修复是相邻但不同的职责。上下文阶段负责事实、关系、证据、能力、知识和限制；输入阶段保证完整问题包合法且可授权地进入模型；模型阶段组织表达；输出阶段验证表达是否有证据支撑。修复只能处理输出表达或结构，不能用模型补齐缺失事实。

## 5. 上下文合同

### 5.1 基本身份

| 字段              | 产品定义                                |
| --------------- | ----------------------------------- |
| `schemaVersion` | 上下文结构版本；版本变化必须可回放                   |
| `rulesVersion`  | 上下文构建规则版本                           |
| `contextType`   | 固定为 `ride_analysis`                 |
| `rideId`        | 必须与 `RideRecord.activity.rideId` 一致 |
| `userScope`     | 用户或会话范围，不能为空                        |
| `analysisRunId` | 本次分析运行标识，绑定输入版本和评测运行                |

### 5.2 主要组成

| 组成                             | 作用                              |
| ------------------------------ | ------------------------------- |
| `sourceInventory`              | 当前可用数据源、字段覆盖、时间范围和质量概览          |
| `capabilities`                 | 原子能力是否可用、依赖、来源、质量和证据            |
| `recordedMetrics`              | 设备或文件直接记录且通过质量门的指标              |
| `derivedMetrics`               | 标准化或确定性公式生成且通过质量门的指标            |
| `estimatedMetrics`             | 系统估算值，必须带估算来源和限制                |
| `featureSnapshot`              | 由时序、分段、事件和跨传感器关系生成的特征           |
| `deterministicAnalyses`        | 计时、地形、爬坡、分区、功率和训练负荷等规则结果        |
| `historicalComparison`         | 有合格历史时的比较、长期负荷和恢复证据             |
| `profileFacts`                 | 本次任务显式授权的 Profile 快照            |
| `knowledgeEvidence`            | 版本化、带引用的领域知识，不是骑行事实             |
| `evidencePackets`              | 每个分析问题的完整事实包、限制和禁止结论            |
| `allowedClaims`                | 所有包内可引用的原子 Claim 去重集合，不能反向删包内证据 |
| `forbiddenClaims`              | 当前不可使用的能力、主题或结论类型               |
| `limitations`                  | 缺失、质量、覆盖、可比性和规则限制               |
| `safetyFlags` / `privacyFlags` | 停止生成和隐私排除边界                     |

## 6. 数据源与证据等级

### 6.1 骑行事实优先级

同一主题出现多个来源时，按以下顺序处理，但不得无来源合并：

1. 设备或文件记录的原始汇总或时序值（`recorded`）；
2. 基于标准化记录的确定性计算（`calculated`）；
3. 有明确方法、质量和误差说明的估算（`estimated`）；
4. 领域知识只解释“如何理解”，不能替代以上三类骑行事实。

设备汇总和序列重算若口径不同，必须保留为不同 Claim，并在包中说明口径、时间基准或覆盖差异。

### 6.2 进入事实层的共同门槛

指标或特征必须同时满足：

- 数值有限、单位合法且语义可解释；

- `qualityStatus=valid`，或明确标记为 `estimated` 并附限制；

- 有合法 `evidenceId`、来源字段、来源单位和 `rideId`；

- 确定性计算值有 `formulaVersion`；

- 与当前分析问题存在明确映射；

- 缺失不填 0，质量失败不伪装成“可能值”。

不能进入事实层的字段必须进入 `unavailable` 或 `limitations`，并说明缺失原因，避免模型把“没有数据”理解成“数值为零”。

## 7. 分析问题与证据矩阵

### 7.1 矩阵使用规则

下表定义目标 V2 的“数据覆盖目录”。“必需证据”缺失时，该维度不作确定性判断；“可选证据”缺失时可以降级解读，但必须降低表达强度。每个维度生成一个完整 `EvidencePacket`，包内保留所有符合条件的指标、特征、区段、事件、历史和限制，不再用 `.find()` 取一项。

| 分析问题      | 必需证据                                                           | 可选证据                    | 主要质量门                            | 可支持结论                                       | 禁止结论                           |
| --------- | -------------------------------------------------------------- | ----------------------- | -------------------------------- | ------------------------------------------- | ------------------------------ |
| 配速执行      | 距离、有效时间、移动或停歇口径、速度汇总或时间对齐速度序列                                  | 巡航段、停歇事件、分阶段均值、路线地形     | 时间基准有效；速度序列覆盖和缺口可解释              | 节奏、停歇影响、阶段变化、执行一致性（需波动证据）                   | 训练计划完成度、意图、比赛策略成功              |
| 爬坡表现      | 爬坡区段或海拔序列、距离、净爬升或平均坡度                                          | 上坡功率、心率、速度、代表性峰值、地形趋势   | 海拔质量、区段边界、最小距离或爬升门槛              | 代表性爬坡难度、区段响应、上坡配速                           | 无区段证据的“爬坡能力提升”、技术或生理诊断         |
| 心率负荷      | 有效心率指标或序列                                                      | 最大心率基线、区间时间、前后段变化、功率配对  | 心率传感器质量；基线来源显式                   | 心率水平、区间分布、漂移或响应（有配对证据时）                     | 健康诊断、恢复完成、因果归因                 |
| 功率输出      | 有效平均功率或功率序列                                                    | NP、标准差或 CV、前后段、峰值窗口、功体比 | 功率覆盖、缺口、零值口径明确                   | 输出水平、波动、峰值和区段差异                             | 无 FTP 时谈 IF、TSS、区间；无波动证据谈稳定    |
| 骑行强度与训练负荷 | 有效功率、用户确认 FTP、NP 和时间基础                                         | IF、TSS、功率区间、训练目标、历史负荷   | FTP `user_confirmed`；NP、时间和功率质量门 | IF、TSS 及其训练负荷含义；相对历史负荷变化                    | 以 TSS 断言恢复、伤病、训练效果；FTP 估算冒充确认值 |
| 踏频策略      | 有效踏频指标或序列                                                      | 踏频区间、功率或速度配对、前后段和峰值     | 踏频质量、有效样本、时间对齐                   | 踏频水平、分布和与输出的关系                              | 无配对证据推断“效率”或骑姿问题               |
| 跨传感器配合    | 至少两种时间对齐的传感器序列或区段                                              | 海拔、停歇、功率或心率或速度相位差       | 共同时间或距离基准、覆盖重叠和缺口                | 同区段的关联、响应先后和伴随变化                            | 把相关说成因果；把缺失传感器补成正常             |
| 相对过去      | 当前锚点、合格历史基线、相同指标和绝对变化                                          | 同路线、同设备、场景和趋势窗口         | `comparable`；历史范围和证据完整           | 本次相对基线变化                                    | 不可比数据的进步、退步、能力提升保证             |
| 长期负荷与恢复   | PMC 窗口门全过（确认 FTP、≥42 自然日、≥10 负荷日），产出 `history.pmc.ctl/atl/tsb` | 无                       | 10.3 节 PMC 统计窗口门槛                | 长期负荷水平、负荷平衡信号（TSB）；TSB ≥ +5 时可支持恢复措辞（FR-08） | 因果、超量训练、伤病诊断、医疗建议、把 TSB 当生理测量  |

### 7.2 输出结构与维度映射

| 用户可见部分   | 允许使用的证据                               |
| -------- | ------------------------------------- |
| 一句话标签    | 一个或多个高置信度维度 Claim；不能只由通用知识生成          |
| 整体评价     | 至少两个独立维度包，或明确说明数据有限                   |
| 当前骑行高光表现 | 本次高置信、可解释且非重复的优势 Claim                |
| 各维度深入解读  | 对应维度完整 EvidencePacket                 |
| 相对过去的表现  | 仅历史比较包；有合格可比历史自动展示，无则不展示为推断           |
| 长期负荷与恢复  | 仅长期负荷与恢复包（PMC 窗口门通过时自动出现，不依赖可比单次骑行）   |
| 建议       | 骑行或历史证据、风险或限制；引用知识时须有适用知识，建议强度与证据强度一致 |

### 7.3 当前标准化数据覆盖矩阵

本矩阵用于验证“当前产品已可用的数据是否有去向”。“进入质量或限制”同样属于被使用：它不一定直接出现在文案里，但必须参与结论资格和表达强度。解析器尚未映射的 FIT 字段不属于当前可用数据。

| 标准化来源            | 字段或数据组                                                                     | 目标用途                          | 进入方式                                |
| ---------------- | -------------------------------------------------------------------------- | ----------------------------- | ----------------------------------- |
| Activity 身份      | `sport/startTime/rideId`                                                   | 室内或户外场景、时间窗口、历史锚点             | 上下文身份、场景或历史比较条件                     |

## 8. 时序特征快照目标规则

### 8.1 从“序列均值”升级为可解释过程特征

`RideFeatureSnapshot` 不发送完整原始点列，但必须足以支撑一次骑行过程判断。每个特征携带 `seriesKey`、时间或距离窗口、有效样本数、覆盖率、缺口统计、加权方式、质量状态、公式版本和证据 ID。

目标特征族包括：

- **水平与分布**：时间或移动时间加权均值、中位数、P10/P25/P75/P90、总体标准差、MAD 或稳健离散度、CV；

- **阶段变化**：前、中、后段，按时间和移动状态切分的均值、差值、斜率、漂移；

- **窗口与事件**：移动窗口峰值、10/20/30 秒功率峰值、停歇、巡航、代表性爬坡和异常缺口；

- **稳定性**：只有存在足够覆盖、有效样本和波动指标时，才能生成稳定或波动类关系 Claim；

- **配对关系**：同一时间或距离窗的功率-心率、功率-速度、功率-踏频、速度-心率和海拔-功率变化；

- **区段关系**：上坡、平路、下坡、巡航段或停歇段中的多传感器特征；

- **数据质量**：连续性、最大缺口、缺失分布、传感器覆盖率、移动或停歇识别置信度。

### 8.2 加权、对齐和缺口规则

- 速度、心率、功率、踏频等过程统计默认使用有效时间或距离加权，不把高频重复采样当成额外骑行时间；

- 停止段不参与“移动配速或移动功率”的统计，但停歇时间作为独立事实保留；

- 不同传感器只有在共同时间或距离窗重叠达到门槛时才能生成关系 Claim；

- 缺口不插值成真实测量值。允许规则化插值时，必须标记 `estimated`、插值时长、最大缺口和公式版本；

- 前、中、后段使用明确的窗口定义，不能只用数组位置替代时间或距离；

- 样本不足、覆盖不足、基准缺失时写入 `featureSnapshot.unavailable`，不能静默丢弃。

### 8.3 最低质量门

具体数值门槛由实现任务冻结，但产品合同必须至少检查：

- 一般统计有足够有效样本；

- 前后段比较有足够的有效时间或距离；

- 区段特征达到最小长度和爬升或停歇门槛；

- 关系特征有共同窗口和最小重叠；

- 所有输出都能回指原始序列证据和规则版本。

当前实现只覆盖序列均值、总体标准差、CV、前后四分之一差值和 NP 或平均功率比，尚未达到本节目标；迁移任务必须以覆盖矩阵验收，而不是只增加字段数量。

## 9. 确定性分析结果进入 AI 的规则

\[详情页]\(骑行数据导入与详情页产品规则说明.md)第 7 节结果仍可复用，但只把与分析问题对应、用户可解释、带规则版本和证据的结果转为 Claim。目标进入完整证据包的结果包括：

- 计时：总时长、移动时长、停歇时长、总均速、移动均速、停歇事件；

- 巡航：巡航总时长和全部合格巡航段；展示层可从完整证据中选择代表性高光；

- 地形：趋势上坡、平路、下坡里程；

- 海拔：最低、最高、范围、正向爬升和海拔质量；

- 爬坡：全部合格爬坡的长度、净爬升、平均坡度、速度、心率和功率区段证据；展示层可选择代表性高光；

- 心率：基线来源、区间时间或比例、前后段变化和质量；

- 踏频：区间时间或比例、阶段变化和质量；

- 功率：平均功率、NP、功体比、质量、波动、峰值窗口；

- 强度与负荷：仅在确认 FTP、NP、时间和质量满足门槛时进入 IF、TSS、区间与训练负荷解释；

- 历史：基线、锚点、变化、历史范围、同路线或同场景证据和长期负荷或恢复摘要。

平滑点、分段中间状态、校准差、完整缺口明细等内部字段默认不单独成为模型事实，但必须在质量判断或限制生成中可追溯。若某个内部字段对支持或禁止一个结论是必需的，应转成明确的质量或关系 Claim，而不是让模型自行猜测。

## 10. Profile、强度、训练负荷与恢复

### 10.1 Profile 版本化快照

Profile 不是骑行文件事实。只有本次调用显式传入、带更新时间和来源的快照字段才能使用：

- 年龄：`years`；

- 身高：`cm`；

- 体重：`kg`，只用于功体比等明确需要体重的计算；

- 最大心率：`bpm`，区分用户填写和系统估算；

- FTP：`W`，只有 `user_confirmed` 才能支撑 IF、TSS、功率区间和基于 FTP 的训练负荷解读。

### 10.2 FTP、NP、IF、TSS 规则

- NP 是骑行事实或确定性计算结果，必须说明计算口径、功率覆盖和缺口质量；

- IF = NP / FTP；FTP 缺失、过期、非确认或质量不满足时，IF 不进入可引用 Claim；

- TSS 必须同时满足 NP、FTP、有效时间和规则版本要求；不能把 TSS 当作健康、恢复或训练效果的直接测量；

- 功率区间依赖确认 FTP；只有显示 NP 而没有 FTP 时，可以解释输出水平，不能补造区间、IF 或 TSS；

- 功体比依赖体重；缺体重只能使用绝对功率，不能生成 W/kg。

### 10.3 长期负荷与恢复

历史默认使用规则：

1. 调用方先查询当前用户在规定窗口内的历史骑行；
2. 系统按同设备、场景、路线、时间范围、数据质量和指标口径完成可比性判断；
3. 只要存在至少一个合格历史快照和可比较指标，就自动加入历史 EvidencePacket；
4. 没有合格历史时，不生成历史 Claim，也不要求用户选择“是否使用历史”。

目标历史包应包含：当前骑行锚点、近 7 或 30 天等窗口的有效骑行数量、总时长或距离、可用 TSS 或负荷总量、最近一次负荷、连续高负荷间隔、休息间隔、同路线或同场景变化、数据覆盖和不可比原因。

一条可比历史只足以支持“与一次过去骑行相比”，不自动解锁长期负荷或恢复分析。长期负荷必须有足够历史窗口、多个有效活动、统一指标口径和覆盖率；恢复相关提示还必须能识别负荷后的时间间隔。无法满足时，只保留单次历史比较，并把长期负荷或恢复能力标记为不可用。

**PMC 统计窗口门槛（RIDE-AI-PMC-01，2026-10-06 冻结）**：长期负荷与恢复统计采用 PMC 模型（公式依据知识库冻结条目“体能-疲劳-状态模型”）——每日 TSS 按 42 天时间常数指数加权为 CTL（长期负荷）、7 天为 ATL（短期负荷），两者之差为 TSB（状态）。开门条件全部满足才产出恢复证据 Claim（`history.pmc.ctl/atl/tsb`，历史类）：FTP 为用户确认值；统计窗口至少 42 个自然日；窗口内至少 10 个有效负荷日；所有 TSS 有限为正。任一条件不满足时两个门保持关闭，只输出对应限制（`FTP_NOT_CONFIRMED`、`INSUFFICIENT_WINDOW`、`INSUFFICIENT_LOAD_DAYS` 等），不伪造负荷数据。

**PMC 单独开包（2026-10-06 用户决策）**：长期负荷与恢复证据进入独立问题包（维度 `longTermLoadRecovery`），准入即上述 PMC 三道门，不依赖“相对过去”包的可比单次骑行门槛；反之“相对过去”包也不再包含 PMC 数据，只保留单次对比类 Claim。知识库中 PMC/恢复相关条目（体能-疲劳模型、负荷双效应、恢复干预、过度训练信号）的适用维度同步迁移至该新维度——没有 PMC 数据时这些知识不挂载，防止模型借知识空谈负荷与恢复。

历史只能支持“负荷信号”和“恢复相关提示”。**恢复结论的证据门（2026-10-06 用户决策，修订此前“一律禁止”规则）**：当断言引用了 `history.pmc.tsb` 证据 Claim 且 TSB ≥ +5（恢复迹象区间）时，允许“恢复良好”等恢复措辞；未达阈值、未引用或无该证据时仍然禁止，且这类失败按可定位错误处理——给至多一次受限模型修复机会，修复失败即降级。无论证据是否充足，仍禁止：把 TSS/TSB 当作生理测量、超量训练或伤病诊断、医疗建议、“恢复完成”的确定性保证。建议表达必须：

- 说明使用的窗口和指标；

- 区分“数据呈现的负荷变化”和“需要用户结合主观感受确认的恢复状态”；

- 历史数据不足、FTP 变化、设备或场景不一致时降低置信度；

- 不把 TSS、心率或骑行间隔单独当作医学或训练处方结论。

## 11. 知识库证据层

### 11.1 可行性结论

在骑行数据上下文、历史数据和 Profile 之外加入“骑行运动科学分析、骑行数据标准、运动科学”知识库是可行且建议的，但必须作为独立 `knowledgeEvidence` 层，不得与骑行事实 Claim 混为一类。

### 11.2 知识证据字段

每条知识证据至少记录：

- `knowledgeId`、主题、适用人群或场景；

- 来源类型（标准、指南、研究综述、专业教材等）；

- 标题、发布机构或作者、版本或发布日期、引用位置；

- 结论强度、适用条件、已知限制和安全边界；

- 检索时间、知识库版本、与本次分析问题的映射；

- 不得替代的骑行事实键。

### 11.3 使用顺序与边界

- 骑行事实决定“发生了什么”；

- 确定性规则决定“从数据中可计算地得到什么”；

- 知识证据解释“通常如何理解、可能有哪些训练含义和注意事项”；

- 当知识与骑行事实冲突时，保留事实并降低解释强度；

- 知识不得生成本次骑行不存在的数字、区段、意图或因果关系；

- 医疗、安全或伤病内容必须触发安全边界，不输出诊断或保证。

建议必须能关联到至少一个骑行或历史 Claim（限制不能单独充当事实依据），并说明相关限制；引用知识时在内部保存其引用。没有适用知识时可以给出基于事实的低风险建议，但不得伪造科学来源或给出需由知识支持的训练处方。

### 11.4 首批知识库内容与引用展示规则（KB-01 已冻结）

首批知识库已按 `RIDE-AI-KB-01` 冻结（版本 `ride-kb-batch1-1.0.0`，2026-10-05），共 8 条、覆盖五个主题（指标定义、功率区间、训练负荷/PMC、恢复、心率漂移）。来源与选型依据见《RIDE-AI-KB-01\_知识库来源调研报告》。本节补充冻结后的运行规则。

**口径统一**：所有训练指标定义（TSS、FTP、NP、IF、CTL/ATL/TSB 等）以 TrainingPeaks 指标术语表为唯一定义基准，其余来源只作解释补充，不另立口径。中英术语对照固定（功能阈=FTP、训练压力分数=TSS、状态=TSB），同一概念不得出现两种名称。

**检索方式**：按维度规则挂载，不使用向量 RAG 检索。知识条目仅在"其 `applicableDimensions` 与本次已有合格问题包的维度存在交集"时进入模型输入；无数据支撑的维度没有问题包，对应知识条目不挂载。理由：首批仅 8 条、需精确可测试、且引用合同（出处、版本、禁止事实键、安全边界）必须完整随行，不能被检索环节裁剪。知识库扩展至数百条后可在检索层引入语义筛选，但引用合同不变。**解释正文随行（2026-10-06 用户决策）**：知识的自撰转述正文（`explanation`）随引用合同一起进入模型输入——知识转述内容只能来自所引知识的解释正文，模型不得凭出处标题自行脑补知识内容或补充数字。

**卡片形态（版权规则）**：知识条目只存自撰转述（`explanation`）与精确出处坐标（`citationLocation`），不复制来源原文。用户想核对原文时按坐标自行查证（书籍翻至对应章节、文章按 URL 访问）。知识条目定位是"结论卡片 + 出处索引"，不是原文摘录。

**展示合同**：解读正文中知识以序号角标形式随句标注（如"按 TrainingPeaks 指标标准，单次超过 300 后恢复需求显著上升\[1]"），页面最底部列出本次引用的知识条目明细（角标序号、标题、发布方、版本、引用位置）。展示层面用户可见每条专业解释的出处，可追溯到具体知识条目。同一知识多次引用复用同一序号，序号按正文出现顺序编号（2026-10-06 用户决策：不在界面上展示"事实/历史对比/知识转述/建议"等结论类型小标签，结论类型申报保留在输出合同中供校验与审计使用）。

**冲突处理**：当知识条目与确定性规则或骑行事实出现口径冲突（如区间边界数值不一致）时，按 11.3 执行——事实与确定性规则优先，知识解释降级。冲突本身视为内容缺陷，按内容治理处理：定位过时或错误的一方 → 修正并升级版本号（知识库升 `ride-kb-batch1-x.y.z`，规则升 `rulesVersion`）→ 以新评测 Run 重新验证，不复用旧盲评结论。

## 12. 原子能力目录

原子能力是“当前能否回答某类问题”的目录，不是旧 DataLevel。目标能力集合包括：

`route`、`distance`、`timing`、`stops`、`cruise`、`speed`、`speedStability`、`elevation`、`terrain`、`climbing`、`heartRate`、`maxHeartRateBaseline`、`heartRateZones`、`heartRateDrift`、`power`、`powerStability`、`powerPeaks`、`normalizedPower`、`verifiedFtp`、`powerZones`、`intensity`、`trainingLoad`、`cadence`、`cadenceZones`、`crossSensorAlignment`、`sensorContinuity`、`userProfile`、`historyComparison`、`longTermLoad`、`recoverySignals`、`sameRouteComparison`、`trend`、`knowledgeEvidence`。

每项能力必须说明：

- `available`；

- 来源（activity、series、deterministic rule、profile、history 或 knowledge）；

- `qualityStatus`（valid、estimated、soft、unavailable）；

- 依赖能力和具体门槛；

- 证据 ID；

- 不可用原因；

- 规则或知识版本和更新时间；

- 可以支持的结论与禁止结论。

典型依赖：

| 能力   | 依赖                                             |
| ---- | ---------------------------------------------- |
| 配速执行 | distance、timing、speed、sensorContinuity         |
| 爬坡表现 | elevation、climbing、timing；可选 power 或 heartRate |
| 心率负荷 | heartRate；区间需 maxHeartRateBaseline             |
| 骑行强度 | power、normalizedPower、verifiedFtp              |
| 训练负荷 | power、normalizedPower、verifiedFtp、timing       |
| 踏频策略 | cadence、timing；关系分析需 crossSensorAlignment      |
| 长期负荷 | historyComparison、trainingLoad、可比窗口            |
| 恢复信号 | longTermLoad、历史间隔、可比负荷；不得等同医疗恢复                |
| 知识解释 | knowledgeEvidence、对应骑行 Claim                   |

当前实现中的能力集合较小，`heartRateZones`、`powerZones`、`trainingLoad` 等部分入口仍可能是 `RULE_NOT_IMPLEMENTED`；本目录是目标完整分析目录，不得在未实现前宣称模型可用。

## 13. 原子 Claim 与证据包

### 13.1 Claim 的定位

Claim 是 AI 可引用的最小事实或关系单元，不是模型结论，也不是页面一行的别名。

每个 Claim 至少包含：

| 字段                             | 定义                                                                |
| ------------------------------ | ----------------------------------------------------------------- |
| `claimId`                      | 全局唯一事实标识                                                          |
| `kind`                         | `metric`、`feature`、`advanced`、`history`、`relation` 或 `limitation` |
| `key`                          | 业务事实或关系键                                                          |
| `value` / `unit`               | 数值和单位；文本限制 Claim 可无数值                                             |
| `confidence`                   | 事实可信度                                                             |
| `evidenceIds`                  | 支撑来源                                                              |
| `provenance`                   | recorded/calculated/estimated/knowledge                           |
| `formulaVersion`               | 确定性规则版本（如适用）                                                      |
| `displayValue` / `displayUnit` | 面向表达的格式化值                                                         |
| `qualityStatus`                | valid/soft/unavailable                                            |
| `supports` / `prohibits`       | 可支持和禁止的结论类型                                                       |

### 13.2 Claim 与来源数据的关系

关系顺序为：

```text
activity / series / profile / history / knowledge
  -> source facts
  -> features and deterministic analyses
  -> atomic Claims (including relation Claims)
  -> EvidencePacket per analysis question
  -> output sections and model input
```

因此，Claim 不是来源数据的另一个平行副本，而是把不同来源转成可引用、可追溯、带质量边界的最小单元。一个维度可以同时包含多个 Claim；单个 Claim 不足以代表该维度的完整证据。

### 13.3 EvidencePacket 合同

每个包至少包含：

- `dimensionId` 和问题定义；

- 全部相关 `claimIds`，按 recorded/calculated/estimated/history/relation 分组；

- 相关时序窗口、区段、事件和覆盖摘要；

- 必需证据是否满足；

- 不可用原因、质量限制和禁止结论；

- 可引用知识证据及其适用条件；

- 建议可用的证据锚点；

- 包版本、规则版本和 `rideId`。

`allowedClaims` 是所有 EvidencePacket Claim 的去重索引，不得反向删除某个包内的合格 Claim。重复 `claimId`、无证据、非有限数值、跨骑行混入或版本不匹配时，上下文校验失败。

## 14. L6/L7 重构规则

### 14.1 L6 目标职责

L6（保留该历史术语，仅用于迁移讨论）改名为“分析问题编排层”，负责：

- 根据能力目录确定可回答问题；

- 为每个问题组装完整 EvidencePacket；

- 标记证据覆盖率和缺口；

- 生成输出结构的排序和展示优先级；

- 生成必须声明的限制和禁止结论；

- 生成知识检索主题，而不是直接把知识当作事实。

L6 禁止：

- 每个槽位只取一个 Claim；

- 只因模型默认不展示就删除相关证据；

- 将一个均值 Claim 充当稳定性、能力或恢复的充分证据；

- 让模型自己寻找历史或 Profile；

- 生成计划、意图或因果 Claim。

### 14.2 L7 目标职责

L7 改为“上下文组装与输入边界校验”。这是必要职责，但实现上可以是轻量的输入构建与校验函数，不要求另建复杂服务：

- 校验 EvidencePacket 的必需证据、去重、来源、`rideId`、引用、数值、单位和版本一致性；

- 校验 Profile、历史和知识证据的授权、适用范围及来源边界，不能把知识解释当成骑行事实；

- 将当前分析问题的完整证据包及必要限制、禁止结论和适用知识组装为固定版本的模型输入；

- 排除原始轨迹、精确坐标、文件名和未授权字段等禁止输入；

- 保留包内全部合格 Claim，不因首项匹配、展示高光、篇幅或模型偏好再次筛选；

- 输入校验失败时阻止模型调用，并向编排方返回可追溯失败原因，由编排方执行既有降级合同。

模型输入仍不是完整原始数据 dump，而是**当前问题相关的完整结构化证据包**。若体积预算不足，应显式标记无法交付的分析问题并降级，不能静默删掉包内合格证据。

### 14.3 模型 API 调用边界

- V2 骑后解读由服务端直接调用模型 API，不再通过扣子（Coze）Workflow 生成或修复解读；现有 Provider 接口、请求追踪和降级合同可复用，但具体 Coze 适配器及 Workflow 变量不能作为 V2 运行依赖。

- 硅基流动是首个待评测渠道，不预设为唯一或最终供应商；模型、供应商和结构化输出能力需用同一批样例比较事实忠实、中文表达、合同通过率、数据处理条款、时延、可用性与成本后冻结。切换渠道不得改变证据、Prompt、输出校验和安全规则。

- 只有 L7 输入校验通过，才可提交版本化完整问题包、必要限制和适用知识；密钥仅在服务端使用，不发送给浏览器，不把原始轨迹、精确位置或未授权资料传给供应商。调用前校验输入体积、模型上下文预算与授权；不足时按问题显式失败并降级，不静默删 Claim。

- 服务端维护小型模型 API 适配边界，配置模型 ID、API 地址、认证、超时、响应体和整体调用预算；可请求供应商的结构化输出能力，但不能因供应商声明 JSON/Schema 合格就跳过本地校验。超时、限流、鉴权失败、响应异常或预算不足按既有 `b0`/`safety_stop` 合同处理，不把 Provider 错误当作可修复的模型输出。

- 每次生成与修复均关联 `analysisRunId`，记录供应商、模型、Prompt/输入/输出 Schema 版本、请求 ID、调用次数、令牌用量（若可用）、延迟、校验错误码和最终降级原因；敏感原文和密钥不进入普通日志。是否记录可回放的最小化输入快照遵循授权及保留规则。

### 14.4 Prompt 与输出合同

- V2 Prompt 单独版本化，与输入和输出 Schema 同步冻结；旧版“只解读当次维度、禁止历史、固定一条建议、从窄化 Candidate Claim 中选择”等条款不得沿用。Prompt 只负责表达目标、结构、引用方式与禁止事项，不能以提示词代替确定性证据门。

- 输入明确区分本次骑行事实、Profile、可比历史、知识解释、限制和禁止结论。模型只能基于包内 Claim 提炼高光；合格历史自动纳入，无历史时不得补写比较；知识不能充当个人骑行事实；低质量和估算必须保留来源与不确定性。

- 输出采用版本化结构：一句话标签、整体评价、可选高光、合格维度、可选历史比较、可选建议及必要限制。每项可检验的数字、区段和定性断言应明确声明所属问题、结论类型、引用的 Claim ID，以及适用时的历史窗口、知识 ID 和限制；建议还需标记依据、适用条件与强度。没有依据时省略可选内容，不强制通用建议填充。

- 结构化引用是校验的输入，不是自动通过的证明。自由文本中的额外判断必须与声明逐项一致；无法可靠核对的高风险或核心判断不得凭附带 Claim ID 放行。

### 14.5 模型输出校验（独立校验器）

**产品承诺**：模型生成的解读不可直接展示——用户看到的每一句话，要么通过本地独立校验，要么被 14.6 的降级兜底替代，不存在中间状态。校验针对**实际交付给模型的输入快照**逐项核对，不以 Prompt 遵循或供应商的结构化输出保证替代。

**三条设计原则**：

1. **结构化申报 + 确定性核对**：输出合同强制每个断言申报结论类型（fact / historyComparison / knowledgeReference / suggestion）与证据引用，校验器只核对申报与文本的一致性，不做语义理解——每条判断可复现、可审计。
2. **宁可误拦、不可漏拦**：误拦的输出还有修复与降级两条路（14.6）；漏拦（错误结论展示给用户）没有第二次机会。误拦率作为新评测 Run 的观察指标，据此校准词表。
3. **语义判断只能收紧、不能放行**：不可复现、不可审计的语义判断（如再用模型做语义校验）只能作为额外收紧手段，不得用于放行；误拦问题通过校准确定性规则的射程（词表与豁免规则）解决，不得靠临时放开规则。

#### 14.5.1 校验内容与射程（S6-01 冻结；RIDE-AI-PMC-01 修订射程）

**（一）整份输出的结构核对**：Schema、必需与可选字段、维度归属、顺序、限制回填、重复或越界引用、知识适用性、隐私与安全表达。

**（二）全局红线门——作用于所有断言，任何位置出现都拦截**：

| 检查项   | 规则                                                                                             |
| ----- | ---------------------------------------------------------------------------------------------- |
| 引用真实性 | 不得编造 Claim 或知识 ID 引用                                                                           |
| 建议锚点  | 每条建议核对至少一个骑行或历史 Claim、相关限制、适用知识（如引用）、质量、不确定性、风险强度和文本本身；限制不能单独支撑建议；知识缺失时仅允许有事实锚点的低风险建议，无可靠依据则省略 |
| 限制回填  | 输入中的限制必须原文回填，不得编造限制                                                                            |
| 数据声明  | 数据不足必须明确声明                                                                                     |
| 因果表述  | "导致、造成、引发"一律禁止；只允许"同时出现、相伴变化"级别的关系描述，不把知识或相关性升级为个人因果结论                                         |

**（三）断言门——仅作用于"下结论"的位置（fact / historyComparison 类结论）**。建议中的目标与操作性措辞（如"想要进步""下次训练计划可加入""尽量保持稳定输出""注意恢复、适当降低负荷"）及知识转述中的方法论措辞不构成对本次骑行或恢复状态的断言，不在射程内（2026-10-06 用户决策：恢复/负荷措辞自全局红线门移入断言门）：

| 检查项  | 规则                                                                                                                                                                          |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 数字命中 | 文本数字须匹配被引用 Claim 的值、单位、来源口径和允许的展示转换。知识转述（knowledgeReference）的数字白名单为所引知识的出处坐标、适用条件或解释正文（解释正文随输入提供，见 11.4 节）——放行"按指标标准，单次超过 300 后恢复需求显著上升"类合法转述，白名单外数字仍按编造拦截（2026-10-06 用户决策） |
| 稳定性  | 稳定/平稳须有支持该结论的波动或过程 Claim，单有均值或笼统 performance ID 不够；阶段、峰值和跨传感器关系须有对应窗口、区段、共同覆盖及质量门                                                                                           |
| 历史对比 | 进步或能力变化须有可比历史及限定范围；长期负荷和恢复须满足历史窗口、覆盖与 FR-08 对应门槛，不能推断恢复完成、伤病或训练效果                                                                                                           |
| 恢复措辞 | 未引用 `history.pmc.tsb` Claim、无该证据或 TSB < +5 时禁止恢复结论（FR-08，RIDE-AI-PMC-01 修订，原"一律禁止且全局生效"改为 TSB 证据门且仅约束断言，见 10.3 节）                                                           |
| 计划完成 | 没有计划 Claim 禁止计划完成断言；当前无此输入，一律禁止                                                                                                                                             |

**（四）结构性剥离与豁免**：区间代号（Z1-Z7）、分段序号、次数/频次表达（"上1次""这2次""每15分钟"）不作为数据值参与数字核对；建议类断言豁免数字核对——补给、时长等操作性数字合法，其事实依据由锚点门保证。

**（五）语义不能可靠判定时的处理**：如自由文本语义不能被既定规则可靠判定，应收紧输出为受约束的结论类型或经验证的表达模板，或拒绝该判断；不能声称关键词匹配已完成全面语义验证。不合格内容不得展示。

### 14.6 有条件修复与降级

校验失败的输出按以下顺序处理。整个修复过程不能改写已校验的 EvidencePacket、Profile、历史或知识快照——出错只可能出在"表达"，不会反过来篡改"事实"。

**（一）不进修复、直接降级的情形**：输入无效、越权/隐私失败、`safety_stop`、Provider 异常或超时，以及（四）所列不可修红线。

**（二）第一步：确定性整理（不调用模型）**。只对无歧义的格式、引用回填或可选高光等局部问题做整理（版本号改正、限制原文回填、编造限制过滤、可选片段删除）；删除可选内容不得掩盖必填核心内容失真；每次整理后必须完整重新校验。

**（三）第二步：至多一次受限模型修复**。触发条件须同时满足：本地整理后仍失败（或无可做的确定性整理）、原输入有效且证据齐全、违规为可定位的非高风险结构或措辞错误（含无 TSB 证据的恢复措辞，RIDE-AI-PMC-01 决策）、整次时延与成本预算允许。修复规则：使用原已校验输入及服务端错误码；原输出视为不可信，只有通过脱敏和字段白名单后才可作为修复参考，否则不再提交原文、仅基于原输入与错误码重新生成；不允许新增事实、Claim、知识、维度或更改证据包。

**（四）不可修红线（不靠反复修复碰运气）**：伪造或缺失关键证据、隐私泄露、医疗/高风险建议、无法可靠定位的核心结论失真、反复出现同类事实性错误。可安全删除的可选片段重新校验后可保留其余输出，否则直接 `b0` 或 `safety_stop`。

**（五）重验与结局**：修复结果仍须通过与首轮相同的独立全量校验；再次失败、超时或超预算即降级，禁止第三次模型调用。四种结局用于审计与评测：首轮通过、本地修复通过、模型修复通过、修复失败（降级）。

## 15. 质量、安全与表达边界

AI 不得：

- 生成上下文不存在的数字或区段；

- 把估算、用户资料或知识结论说成设备实测；

- 把缺失值当作 0；

- 没有波动或过程证据时说“稳定、平稳、保持良好”；

- 没有可比历史时说“进步、退步、长期负荷增加”；事实或历史对比断言中没有引用 TSB ≥ +5 的 PMC 证据时说“恢复良好”（建议中的恢复/负荷操作性措辞不受此限，2026-10-06 用户决策）；

- 没有确认 FTP 时引用 IF、TSS、FTP 区间或负荷等级；

- 把相关关系说成因果，把知识共识说成个人诊断；

- 以“符合训练计划”“完成目标”等不存在的计划信息作结论；

- 暴露精确位置、文件名或未授权个人资料。

质量为 `soft` 时必须降低表达强度并说明部分缺失；不可用时只能说明原因。出现 `stop_generation` 或 `critical_safety` 时返回 `safety_stop`，不生成普通解读。

## 17. 产品验收标准

### 17.1 证据完整性

- 每个可用分析问题生成一个完整 EvidencePacket；

- 包内包含该问题所有通过质量门的基础、时序、区段、关系、确定性、历史和 Profile Claim；

- 不再存在“第一个匹配 Claim 覆盖其他同主题证据”的路径；

- L7 的输入快照能证明当前问题包内全部合格 Claim 已进入模型输入，且禁止输入字段已被排除；失败时有明确原因，不静默裁剪；

- 覆盖矩阵能追踪 `source -> feature -> capability -> Claim -> dimension -> output`，无未解释断点。

### 17.2 分析充分性

- 配速、爬坡、心率、功率、强度或训练负荷、踏频和跨传感器问题均有必需或可选证据和禁止结论；

- 时序特征能支持阶段、波动、峰值和对齐关系判断；

- FTP、NP、IF、TSS 的依赖被显式校验；

- 有合格历史时自动产生历史包，支持长期负荷或恢复提示；无历史时不产生历史推断。

### 17.3 事实与安全

- 无波动证据不得生成稳定性结论；

- 无计划 Claim 不得出现计划完成或符合计划；

- 相关关系不得自动升级为因果或能力提升；

- 估算、软质量、知识和用户资料都保留来源语义；

- 原始轨迹、精确坐标和文件名不进入模型。

- 模型输入前的完整性、授权与隐私校验和模型生成后的事实性与表达校验分别通过。

- 直连模型 API 不依赖 Coze Workflow；模型调用失败不误入输出修复；密钥和敏感原文不进入客户端或普通日志。

- 每个定性断言与建议的结论类型、对应 Claim、适用知识及限制可核对；输出不通过时只有符合修复准入的错误可再调模型一次，二次仍失败不展示。

### 17.4 评测

- 新规则冻结后建立全新评测 Run ID，不续用 V1 `T002-V04` 作为证明；

- 至少比较事实忠实、不确定性、洞察价值、行动性四项；

- 新增稳定性、能力提升、恢复、训练计划和因果的反例集；

- 验证“完整证据进入上下文”与“模型只引用有证据 Claim”两层均通过。

- 对候选供应商/模型运行同一批样例，记录首轮通过、确定性修复通过、模型修复通过、拒绝降级、端到端延迟、用量与成本；不以修复后通过率掩盖首轮事实错误。

## 18. 未决与后续实现决策

以下事项在实现前需要冻结，不在本设计文档中擅自填写实现细节：

1. 各类时间或距离加权和窗口的具体数值门槛；
2. 长期负荷窗口、TSS 汇总方法和恢复提示的具体文案；
3. Profile 快照的来源权限、过期规则和隐私同意；
4. 知识库的首批来源、版权范围、更新频率和检索组件；
5. 关系 Claim 的统计方法、最小共同覆盖和相关性表达阈值；
6. 输出结构中每个维度的最大篇幅和排序策略；
7. 直连 API 的最终渠道、模型、结构化输出能力、数据处理条款及切换条件（硅基流动为候选，非已验收结论）；
8. 一次生成加可选一次修复的整体时延、令牌与费用预算，以及各类输出错误的可修复白名单和语义校验覆盖范围。

这些决策完成前，不得把当前实现入口标记为已支持 V2 全量分析。
