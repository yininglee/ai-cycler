# Agent 结构与路由：六场景满足度评估

- 日期：2026-10-27
- 评估对象：现有对话 Agent 的**结构与路由**（不是交互设计细节）
- 评估问题：这 6 个场景，现有结构**撑不撑得住**？路由够不够？
- 结论：**不满足。** 路由覆盖了「问什么」，完全没覆盖「怎么交互」

---

## 一、结论先说

| 评估维度 | 现状 | 6 场景需要 | 裁定 |
|---|---|---|---|
| **意图**（问什么） | 16 条 route | 6 个场景都能落位 | ⚠️ **部分满足**：③④ 落在占位模板，是空壳 |
| **动作**（这句要干什么） | 4 个：`deterministic_reply` / `tool_then_model` / `safety_stop` / `reject` | 还要「给选项」「产出结构化物」「写确认」 | ❌ **不满足**，缺 3 类 |
| **状态**（跨轮记住什么） | 摘要 4 字段：`question / route / rideAnchor` | 要记住「用户选中了哪条记录 / 哪个目标」 | ❌ **不满足** |
| **产出**（能交出什么） | 600 字纯文本 + 3 个引用数组 | 计划要结构化（周/课/强度/目标） | ❌ **不满足** |
| **校验**（能拦什么） | 文本证据溯源 + 数字 + 违禁词 | 计划要 schema 校验 + 处方硬门 | ❌ **不满足** |
| **动作落库**（能写吗） | 写操作一律拒绝 | 计划确认必须写入 | ❌ **不存在** |

**一句话**：现有 Agent 只有一种形态——**「读懂问题 → 取数 → 说一段话」**。你描述的 6 个场景需要三种新形态：**「给你几个选项，你选一个」**、**「产出一个可查看可确认的东西」**、**「你真的确认了才生效」**。这三种形态在结构里都没有位置。

**这不是加个字段能解决的**，所以要先把结构改对，再谈交互。

---

## 二、为什么不能只看 route

路由只回答一个问题：**这句话属于哪个意图**。但一个场景能不能跑，取决于五件事是否都有位置：

```
意图能不能落位 → 动作能不能表达 → 状态能不能保持 → 产出能不能承载 → 校验能不能兜住
```

现有结构在第 1 项上做得不错（16 条覆盖了几乎所有骑行话题），第 2~5 项基本是空的。**上一轮讨论的"去路由化"只解决第 1 项（而且是把 16 条压成 3 条），跟第 2~5 项完全正交。**

## 三、八层满足度矩阵

| 层 | 现状能力 | 6 场景真正需要 | 裁定 | 缺口 |
|---|---|---|---|---|
| **L0 入口** | 会话 / 长度 / 限流 / 摘要网关 | 同一套够用 | ✅ | — |
| **L1 路由·意图** | 16 route（含 2 个占位） | 6 个场景都能落位 | ⚠️ | ③④ 空壳；其余 4 个"能落但不合手" |
| **L1 路由·动作** | 4 个 `action` | + `select` + `produce_artifact` + `confirm_write` | ❌ | **G-1** |
| **L2 锚点/状态** | 日期 / 序数 / 继承；确认轮只认「是的·最近一次·日期」 | 点选任意记录；选训练目标；选计划槽位 | ❌ | **G-2** |
| **L3 取数** | 9 只读工具（6 条记录绑定 + 3 条全局） | 选记录✅；计划需 `get_active_plan` + 写工具 | ⚠️ | 计划域工具缺失 |
| **L4 生成** | 6 字段：`reply ≤600 字` + claimIds/capabilityKeys/knowledgeIds | 计划需结构化载荷（周×课×强度×目标） | ❌ | **G-3** |
| **L5 校验** | 引用溯源 + 数字等价类 + 违禁词 | + 计划 schema + 处方硬门 | ❌ | **G-4** |
| **L6 修复/降级** | 1 次修复 + Claims 摘要兜底 + 16 类降级码 | 够用 | ✅ | — |
| **L7 输出/前端** | `reply + rideAnchor + trace + validation` | + `choices[]` + `artifact` + `actions[]` | ❌ | **G-3** |
| **写路径** | 不存在（`WRITE_VERB × WRITE_OBJECT` 一律拒） | 计划确认落库 + 审计 | ❌ | **G-5** |

## 四、六场景逐条裁定

| # | 场景 | 落在哪个 route | 结构化缺口 | 裁定 |
|---|---|---|---|---|
| ① | 问"骑行数据分析"→ 追问哪一次 → **给记录列表** → 点选 → 分析 → **深度分析入口** | `current_ride`（+ 循环可选） | **动作缺 `select`**、**状态缺选择槽位**、**产出缺 `choices[]` / 深度分析入口字段** | ❌ 结构不满足（部件全在，通路没开） |
| ② | 轻问只给简单数据 + 引导深度分析 | `current_ride`（`dims=summary`） | 只缺"引导语 + 入口字段"（同 ① 的产出缺口） | ⚠️ 差一步 |
| ③ | 训练计划生成 → 追问目标 + **给目标选项** → 生成 → **让用户确认** | `training_plan`（占位） | 动作缺 `select` + `produce_artifact` + `confirm_write`；产出缺结构化；校验缺硬门；写路径不存在；计划实体不存在 | ❌ 结构完全不满足 |
| ④ | 问计划 → 展示并解释当前计划 / 没有则引导生成 | `training_plan` / `training_supervision`（占位） | 计划实体不存在；缺 `get_active_plan` 工具；缺结构化展示形态 | ❌ 结构完全不满足 |
| ⑤ | 知识问答 | `kb_qa` | 无结构缺口 | ✅ 满足 |
| ⑥ | 水平评估 | `level_assessment` | 无结构缺口（打磨点是校验词表，不是结构） | ✅ 满足 |

**读法**：⑤⑥ 是"结构上已经对了，只是质量要磨"；②是"结构上差一个出口"；①③④ 是"结构上缺形态"。

## 五、五个结构性缺口（按严重度排）

### G-1 动作维度只有 4 个值，缺三种交互形态
`action ∈ { deterministic_reply, tool_then_model, safety_stop, reject }`

这 4 个值全部在描述「**怎么回答**」，没有一个描述「**要用户做什么**」。所以：
- 想给用户一张记录列表让他选 → 只能退回 `deterministic_reply`，把列表塞进 600 字话术里（不可点、不可枚举、数量受限）
- 想产出一份计划让用户确认 → 只能塞进 `reply` 正文（600 字，装不下周课表，且无法校验）
- 想让"确认"生效 → 没有对应动作，只能拒绝（现在的写拦截就是这么来的）

### G-2 状态槽位里没有"选择"，只有"锚点"
摘要槽位=`{question, route, rideAnchor?}`，且锚点只存**日期**。确认轮（`detectAnchorConfirmation`）的接受范围是硬编码的三种：`是的/最近一次` + `显式日期`。

后果：**"选择"只能被表达成"再打一句日期"**。记录一多（>7 条）用户就得记住日期去打——这不是交互，这是让用户做字符串匹配。
而且锚点存日期不存 `rideId`，同一天两条记录无法区分（会按"当天最晚出发"静默选一条）。

### G-3 产出一个形态：600 字文本，没有结构化载荷
输出合同 `ride-chat-output-v0.2` 是 `{schemaVersion, route, reply ≤600, claimIds, capabilityKeys, knowledgeIds}`。

这适合"回答一个问题"，不适合"交付一个东西"。计划、记录列表、可点选按钮，都需要**与文本并行的结构化载荷**，且必须能被校验、能被前端直接渲染。现在没有任何通道。

### G-4 校验只认文本，不认结构化物
现有校验做的是：回复里的每个数字能否溯源、claimIds 是否在集合内、有没有违禁词。它能保证"说的话有出处"，**保证不了"这份计划合理"**（周负荷增幅、强度区间、恢复日、伤病禁忌）。这两类校验的机制完全不同：前者是字符串与集合，后者是规则引擎。

### G-5 没有写路径
写操作现在是 `WRITE_NOT_SUPPORTED` 直接拒（这是对的，在写工具存在之前）。但"让用户确认计划"本质是一次写。缺的不只是工具，还有：确认令牌、二次确认、审计留痕、写后再校验。

## 六、去路由化能解决这些吗？——不能，两者正交

| | 去路由化解决 | 这里的问题 |
|---|---|---|
| 意图层 | ✅ 16→3，删掉"用路由表达工具选择" | 意图落位本来就是满足的 |
| 动作层 | ❌ 完全不涉及 | G-1 |
| 状态层 | ❌ 完全不涉及（rideRef 只是把"记录选择"从正则改到参数） | G-2 |
| 产出层 | ❌ 完全不涉及 | G-3 |
| 校验层 | ❌ 只提到加强，没提结构化校验 | G-4 |
| 写路径 | ❌ 完全不涉及 | G-5 |

**所以：做完去路由化，①② 仍然只能靠"再打一句日期"，③④ 仍然只能回"正在路线图中"。** 这两件事要分开排期，别指望一个解决另一个。

> 反过来也有价值：G-1/G-2 里"选记录"这条，正好是去路由化方案中 `rideRef` 的 UI 面。两件事在这一点上可以合并实现，其余部分互不影响。

## 七、要撑住 6 个场景，最小结构改动集（MSC）

| 编号 | 改动 | 撑住哪些场景 | 规模 |
|---|---|---|---|
| **MSC-1** | `action` 扩为 7 值：+ `select`、+ `produce_artifact`、+ `confirm_write` | ①②③④ | 小（枚举 + 分派分支） |
| **MSC-2** | 摘要槽位加 `choice {kind, id}`；`rideAnchor` 退化为纯展示；点选必须传 `rideId` | ①③ | 中（合同升 v0.3 + 前端） |
| **MSC-3** | 新增 `artifact` 通道：与 `reply` 并行的结构化载荷（`{kind:"ride_list"｜"plan"｜"goal_options", payload}`），不占 600 字额度 | ①②③④ | 中（输出合同 + 前端组件） |
| **MSC-4** | 校验分层：文本校验（现有）＋ artifact 校验（schema + 领域规则） | ③ | 中（新增校验器） |
| **MSC-5** | 写路径：确认令牌 + 写工具 + 审计 | ③ | 大（AGT-F 范畴） |

**只做 MSC-1/2/3** → ①② 完整、③④ 的"追问与选择"部分完成（但生成与确认仍缺）。
**加上 MSC-4/5** → ③④ 完整，但还需计划实体与生成 workflow（AGT-F）。

## 八、不改的后果（会怎么退化）

| 场景 | 不做的表现 |
|---|---|
| ① | 用户问"分析一下骑行数据"，助手回一段文字问"是哪一次"，用户只能**再打一句日期**；记录超过 7 条基本不可用；"深度分析入口"只能写进文字里（不可点） |
| ② | 能答，但没有"往下走"的路径，用户不知道还能深度分析 |
| ③ | 永远回"正在路线图中"——**这不是能力没做，是结构里没有"产出计划"的位置** |
| ④ | 永远无计划可看 |

## 九、这件事在里程碑里的位置（评估的真正发现）

| 缺口 | 归属 | 状态 |
|---|---|---|
| G-5 写路径 + G-1 的 `confirm_write` + 计划实体 | AGT-F | **已规划**（Backlog，前置 P6） |
| G-4 结构化校验（处方硬门） | AGT-F | 已规划（放行门：硬门违规=0、采纳率≥60%） |
| **G-1 `select` / `produce_artifact`** | **无归属** | ⚠️ **规划盲区** |
| **G-2 选择状态槽位** | **无归属**（D 里程碑是"上下文三层"，但没列 choice） | ⚠️ **规划盲区** |
| **G-3 artifact 输出通道** | **无归属** | ⚠️ **规划盲区** |

**这是本次评估最该记住的一条**：交互骨架（选择 / 产物 / 确认）目前**没有任何里程碑承接**。AGT-C 是"生成层质量"，AGT-D 是"上下文记忆"，AGT-F 是"计划与写路径"——三者都不包含"让用户点选"和"产出结构化物"。

所以建议新增一个工作项（如 **AGT-H 交互骨架**：MSC-1/2/3），前置 AGT-C，可与 D 并行；否则等 F 做完会发现"计划生成了，但没有界面能确认它"。

## 十、直接回答你的问题

- **路由满足吗？** 意图层面基本满足（16 条能落位），但**"路由 = 意图"这个设计本身对交互场景是不够的**——交互需要的是动作，不是分类。
- **结构满足吗？** 不满足。缺 3 个动作、1 类状态、1 种产出形态、1 层校验、1 条写路径。
- **要不要先去路由化？** 可以做，但它解决的是另一件事（取数路径统一），**不能替代这里任何一项**。若排期紧，建议先做 **MSC-1/2/3**（①②立刻可用、③④ 打好交互地基），去路由化作为并行的架构治理。
