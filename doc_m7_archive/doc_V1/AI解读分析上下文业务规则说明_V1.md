# AI 解读分析上下文业务规则说明

> 文档定位：V2 重构产品规则文档
>
> 视角：产品经理业务规则
>
> 状态：当前实现基线，后续随 AI 解读产品规则重构迭代
>
> 关联文档：[骑行数据导入与详情页产品规则说明](骑行数据导入与详情页产品规则说明.md)、[技术方案_AI骑行伙伴_V2](技术方案_AI骑行伙伴_V2.md)

## 1. 文档目的

本文件定义一次骑行请求 AI 解读前，系统如何从标准化骑行记录中整理出 AI 可使用的分析上下文。

本文件解决以下产品问题：

- AI 解读使用哪些骑行事实和分析结果；
- 哪些数据可以作为 AI 的事实依据，哪些数据必须标记不可用；
- 页面展示的数据与 AI 上下文之间是什么关系；
- 数据质量不足、用户资料缺失或存在隐私风险时，AI 应如何收敛表达；
- 如何保证 AI 输出中的数字能够追溯到标准化记录或确定性规则。

本文件不定义 FIT/GPX 的底层解析字段，也不定义详情页的完整展示布局。导入字段和详情页展示以《骑行数据导入与详情页产品规则说明》为准。

## 2. 产品结论

### 2.1 AI 上下文不是原始文件副本

AI 不直接读取 FIT/GPX 文件，也不直接读取完整的 `RideRecord` JSON。系统先完成解析、标准化、校验和确定性分析，再将可用于解读的事实整理为上下文。

### 2.2 AI 上下文不是详情页数据的简单复制

详情页和 AI 都消费同一条标准化 `RideRecord`，但目标不同：

| 消费方 | 目标 | 数据组织方式 |
|---|---|---|
| 详情页 | 展示可追溯的骑行事实和图表 | 按摘要、分析、数据 Tab 组织；保留页面需要的字段 |
| AI 上下文 | 支持受约束的骑行解释 | 按事实、特征、能力、限制和证据引用组织 |
| AI 输出 | 面向用户表达洞察 | 只能基于被选中的上下文证据生成解释 |

因此，详情页上可见的字段不一定全部进入 AI；AI 可使用的特征也不一定作为独立数字行出现在详情页。

### 2.3 AI 上下文没有整体 DataLevel

当前上下文不使用旧的 `dataLevel=L1/L2/L3`，也不使用由等级统一决定话题权限的规则。AI 能否谈论某个主题，由该主题对应的原子能力、事实、质量状态和依赖条件分别决定。

`source: "b0"` 只表示本次 AI 解读没有交付有效结果时的降级来源，不是骑行数据等级，也不是 AI 上下文等级。

## 3. 适用范围与输入前提

### 3.1 适用请求

本规则适用于用户在骑行详情页发起的单次骑行 AI 解读请求。包括：

- 首次请求骑行解读；
- 用户点击重试；
- AI 解读服务暂时不可用后的再次请求。

### 3.2 必须输入

上下文构建至少需要：

- 一条与请求 `rideId` 匹配的标准化 `RideRecord`；
- `RideRecord.activity` 和 `RideRecord.series` 的完整结构；
- 活动指标的来源、质量和证据元数据；
- 时序字段及其序列 metadata；
- 当前规则版本。

### 3.3 可选输入

上下文合同可以接收以下可选信息：

- 用户资料：年龄、身高、体重、最大心率、FTP；
- 历史比较快照：近 30 天或同路线的可比结果；
- 业务安全标记；
- 已经计算完成且与当前 `rideId` 匹配的特征快照。

可选输入只有在来源可信、与当前骑行匹配并通过校验时，才能进入上下文。

## 4. 上下文构建总流程

```text
RideRecord
  -> 记录和序列校验
  -> 构建时序特征快照
  -> 构建原子能力画像
  -> 运行确定性分析规则
  -> 生成带证据的 Claims
  -> 汇总 Profile/历史（若提供）
  -> 汇总不可用原因、限制和隐私边界
  -> 校验 RideAnalysisContext
  -> 计算 AI 解读资格
  -> 按解读维度筛选最终模型输入
```

上下文构建与 AI 文案生成是两个阶段。上下文阶段只负责事实、证据、能力和限制；模型阶段负责在这些约束内组织自然语言。

## 5. 上下文产品合同

### 5.1 基本身份字段

上下文必须包含：

| 字段 | 产品定义 |
|---|---|
| `schemaVersion` | 上下文结构版本，当前为 `0.3` |
| `rulesVersion` | 上下文构建规则版本，当前为 `ride-analysis-context-rules-v0.3` |
| `contextType` | 固定为 `ride_analysis` |
| `rideId` | 当前骑行标识，必须与 `RideRecord.activity.rideId` 一致 |
| `userScope` | 用户或会话范围，不能为空 |

上下文版本用于保证 AI 输入合同可追溯。规则版本变化时，历史分析运行记录应能够识别使用的规则版本。

### 5.2 上下文主要组成

`RideAnalysisContext` 由以下部分组成：

| 组成 | 作用 |
|---|---|
| `capabilities` | 说明各类分析能力是否可用、依赖什么、质量如何 |
| `recordedMetrics` | 设备或文件直接记录且通过质量校验的指标 |
| `derivedMetrics` | 标准化流程中由确定性公式生成且通过质量校验的指标 |
| `estimatedMetrics` | 系统估算指标，必须带估算来源和公式信息 |
| `featureSnapshot` | 从时序数据生成的统计特征及不可用项 |
| `historicalComparison` | 可选的历史比较快照 |
| `profileFacts` | 被授权进入本次上下文的用户资料事实 |
| `allowedClaims` | AI 可以引用的事实声明集合 |
| `forbiddenClaims` | 当前不可使用的能力键集合 |
| `limitations` | 质量不足、依赖缺失和算法限制 |
| `safetyFlags` | 安全策略对生成行为的约束 |
| `privacyFlags` | 已执行的隐私排除边界 |

## 6. 数据进入上下文的分层规则

### 6.1 第一层：标准化活动指标

系统遍历 `activity.metrics`，只允许同时满足以下条件的指标进入 AI：

1. 指标存在；
2. 数值有限且可解释；
3. `qualityStatus=valid`；
4. 指标具有合法的 `evidenceId`、单位、来源字段和来源单位；
5. 若为确定性计算值，具有 `formulaVersion`。

指标按 `provenance` 分桶：

- `recorded` -> `recordedMetrics`；
- `calculated` -> `derivedMetrics`；
- `estimated` -> `estimatedMetrics`。

当前规则明确排除 `elevationLossM`，因为它属于需要在专门 AI 任务中重新定义消费口径的事实，不自动进入通用解读上下文。

缺失指标不填 0；质量不通过的指标不以“可能值”形式传给模型。

### 6.2 第二层：时序特征快照

系统从 `series.points` 生成 `RideFeatureSnapshot`，不把完整原始点列作为通用文本上下文发送。

当前可生成的特征包括：

| 主题 | 特征 |
|---|---|
| 速度 | 序列均值、标准差、变异系数、前后段均值变化 |
| 心率 | 序列均值、标准差、前后段均值变化 |
| 功率 | 序列均值、标准差、变异系数、前后段均值变化、NP/平均功率比 |
| 踏频 | 序列均值、标准差、变异系数、前后段均值变化 |
| 海拔 | 最低海拔、最高海拔、海拔范围、正向爬升 |

序列特征的通用门槛：

- 对应 capability 必须可用；
- 序列 metadata 必须有效；
- 一般统计至少需要 5 个有效值；
- 前后段变化至少需要 8 个有效值；
- 前后段变化使用序列前后各 `floor(n/4)` 个样本的均值差；
- 标准差使用总体标准差；
- 变异系数只有在均值大于 0 时计算。

无法满足条件的特征进入 `featureSnapshot.unavailable`，并记录原因和所需能力，不得静默删除后让模型误以为“没有变化”。

### 6.3 第 7 节确定性分析结果

系统可以复用详情页使用的确定性规则，但 AI 消费的是经过筛选的分析 Claims，而不是规则对象的全部内部字段。

当前进入高级 Claims 的结果包括：

- 计时：总均速、移动均速、停歇时间；
- 巡航：巡航总时长、最多 3 个代表性巡航段；
- 地形：趋势上坡、平路、下坡里程；
- 海拔：最低、最高和海拔范围；
- 爬坡：最多 3 个代表性爬坡的长度、净爬升和平均坡度；
- 心率：分区基线和区间分布；
- 踏频：区间分布；
- 功率：质量、平均功率、NP、IF、TSS、功体比、功率区间和 10/20/30 秒峰值功率。

内部规则字段，例如平滑点、缺口明细、分段中间状态、校准差和完整不可用原因集合，原则上只用于计算、质量判断或生成限制，不自动逐项暴露给模型。

### 6.4 用户资料

只有本次任务明确需要且调用方显式传入的 Profile 字段，才能进入 `profileFacts`。

可用字段及口径：

- 年龄：单位 `years`；
- 身高：单位 `cm`；
- 体重：单位 `kg`，只用于功体比等需要体重的分析；
- 最大心率：单位 `bpm`，必须记录是用户填写还是系统估算；
- FTP：单位 `W`，仅 `user_confirmed` 才能支撑功率区间、IF 和 TSS。

Profile 不是骑行文件中的事实。AI 不得把用户填写或系统估算的个人资料描述成设备测量值。

### 6.5 历史比较

只有已经完成可比性判断的历史快照才能进入上下文：

- 当前骑行必须是历史快照的 anchor；
- 指标必须存在 baseline、anchor、绝对变化和证据；
- comparability 必须为 `comparable`；
- 不可比的历史结果不生成历史 Claim；
- 同路线比较必须通过路线签名和场景规则。

历史比较是附加证据，不得在没有比较资格时由 AI 自行推断“进步”“退步”或“能力提升”。

## 7. 原子能力规则

### 7.1 能力集合

当前能力键包括：

`route`、`distance`、`timing`、`speed`、`elevation`、`heartRate`、`maxHeartRateBaseline`、`heartRateZones`、`power`、`normalizedPower`、`verifiedFtp`、`powerZones`、`trainingLoad`、`cadence`、`userProfile`、`historyComparison`、`sameRouteComparison`、`trend`。

### 7.2 能力状态

每项能力必须说明：

- `available`：当前是否可用；
- `sources`：来自活动、时序、用户资料或确定性规则；
- `qualityStatus`：有效、估算或其他质量状态；
- `dependencyKeys`：依赖的其他能力；
- `evidenceIds`：支撑该能力的证据；
- `unavailableReason`：不可用原因；
- `provenance`：来源及更新时间等信息。

能力不可用不代表整条骑行记录不可用。它只限制对应主题，其他独立事实仍可使用。

### 7.3 典型依赖

| 能力 | 主要依赖 |
|---|---|
| 速度 | 时间能力、速度指标或速度序列 |
| 心率区间 | 心率能力、最大心率基线 |
| 功率区间 | 功率能力、用户确认 FTP |
| 训练负荷 | 功率能力、用户确认 FTP |
| 功体比 | 功率能力、用户体重 |
| 同路线比较 | 历史比较、路线能力 |

如果依赖不满足，系统记录 `DEPENDENCY_UNAVAILABLE` 或对应原因，不允许 AI 自行补齐依赖。

### 7.4 当前实现中的规则状态

上下文能力合同支持心率区间、功率区间和训练负荷，但能力画像中的部分入口可能标记为 `RULE_NOT_IMPLEMENTED`；详情页的 `ride-zones` 和 `ride-power` 仍可有独立计算结果。

产品上必须区分：

- “详情页能够计算”；
- “能力画像标记可用”；
- “该结果已经进入本次 AI Claims”；
- “模型最终被允许引用”。

这四者不是同一个状态。

## 8. Claims 业务规则

### 8.1 Claim 的定位

Claim 是 AI 可引用的、带来源的最小事实单元。它不是模型生成的结论，也不是页面展示行的简单别名。

每个 Claim 至少包含：

| 字段 | 定义 |
|---|---|
| `claimId` | 全局唯一的事实标识 |
| `kind` | `metric`、`feature`、`history` 或 `advanced` |
| `key` | 业务事实键 |
| `value` / `unit` | 可计算的数值和单位（文本型限制 Claim 可无数值） |
| `confidence` | 事实可信度 |
| `evidenceIds` | 支撑该事实的来源证据 |
| `provenance` | recorded/calculated/estimated 等来源类型 |
| `formulaVersion` | 确定性规则版本（如适用） |
| `displayValue` / `displayUnit` | 面向表达的格式化值 |

### 8.2 Claim 来源

- `metric`：来自 `activity.metrics` 的合格指标；
- `feature`：来自 `RideFeatureSnapshot` 的时序统计特征；
- `history`：来自已通过可比性判断的历史快照；
- `advanced`：来自第 7 节确定性分析规则的结果。

同一主题可以同时有多个来源。若设备汇总值和序列重算值口径不同，必须保留不同 Claim 或不同 evidence，不得在没有来源说明的情况下合并为一个数值。

### 8.3 去重与证据要求

- `allowedClaims` 中 `claimId` 必须唯一；
- 每个 Claim 至少有一个 `evidenceId`；
- Claim 数值必须有限；
- `rideId`、规则版本和证据来源必须可回溯；
- 同一 `claimId` 重复出现时，上下文校验失败，不交给模型。

## 9. 能力、资格与最终模型输入

### 9.1 上下文校验

在计算 AI 资格前，必须校验：

- Schema 和规则版本受支持；
- `rideId`、`userScope` 有效；
- 完整能力键集合存在；
- 不存在旧 `dataLevel` 字段；
- 隐私标记至少包含原始轨迹和精确坐标排除；
- Feature Snapshot 与当前骑行匹配；
- 历史快照（如有）与当前骑行匹配；
- Claims 无重复、数值有效且证据不为空。

上下文校验失败时，不进入普通 AI 生成流程。

### 9.2 解读资格

满足以下条件时，骑行才具备普通 AI 解读资格：

1. 上下文校验通过；
2. 没有触发安全停止标记；
3. 记录没有被完整判定为无效；
4. 至少有一个有效 Activity metric Claim；
5. 至少有一个可用的特征、历史或高级分析来源。

资格状态分为：

- `eligible`：可以生成受约束的 AI 解读；
- `not_eligible`：数据不足，返回 AI 降级；
- `blocked`：上下文不合法、记录拒绝或触发安全停止。

### 9.3 解读维度筛选

当前候选解读维度包括：

- 路线节奏；
- 地形与爬坡；
- 心率；
- 功率；
- 踏频；
- 配速稳定性。

某个维度必须同时具备：

- 一个基础事实 Claim；
- 一个特征或高级分析 Claim；
- 对应的能力和质量条件。

缺少任一部分，该维度不进入候选输入，并记录排除原因。

默认模式最多聚焦优先级最高的 3 个维度；当前骑后 API 以 `expanded` 模式构建全部合格维度，再由展示层决定默认展示数量。

### 9.4 最终模型输入

最终模型输入只保留候选解读实际引用的 Claim、对应视觉引用、限制、隐私标记和安全标记。

未被候选维度引用的 `allowedClaims` 不应因为“已经在上下文中”就自动发送给模型。历史解读维度当前在非历史输入中明确排除。

## 10. 隐私、安全与表达边界

### 10.1 默认排除项

AI 上下文默认包含以下隐私边界：

- `raw_track_excluded`：不发送原始轨迹点；
- `precise_coordinates_excluded`：不发送精确经纬度；
- `source_filename_excluded`：不发送上传文件名；
- `untrusted_free_text_excluded`：不发送未受信任自由文本。

路线如需作为证据，只能使用相对路线、路线签名或已计算的路线特征，不能还原用户精确位置。

### 10.2 AI 表达限制

AI 不得：

- 生成上下文中不存在的数字；
- 把估算值说成设备实测值；
- 把缺失值当作 0；
- 把不可比的历史差异说成训练进步或退步；
- 在 FTP、最大心率或体重缺失时虚构功率区间、IF、TSS 或 W/kg；
- 将详情页的可见字段自动扩展成 AI 已知字段；
- 暴露原始文件名、精确坐标或未授权个人资料。

质量为 `soft` 的结果必须带“部分缺失/仅供参考”语义；不可用结果只能说明缺失原因，不能编造替代值。

### 10.3 安全停止

当 `safetyFlags` 包含 `stop_generation` 或 `critical_safety` 时，禁止继续生成普通 AI 解读，返回 `safety_stop`。安全停止优先级高于数据充足性。

## 11. 降级和用户影响

### 11.1 B0 降级

以下情况可返回 `source: "b0"`：

- 数据不具备解读资格；
- AI 功能关闭；
- Provider 未配置或调用失败；
- Provider 输出校验失败；
- 重试后仍未获得合格解读。

`b0` 是请求结果状态，不会覆盖、删除或改变详情页的标准化数据和确定性分析。

### 11.2 Safety stop

安全停止返回 `source: "safety_stop"`。它与普通数据不足降级区分记录，并且不应以普通 AI 文案替代。

### 11.3 用户可见原则

- AI 不可用时，详情页的确定性事实仍可正常查看；
- 单个主题不可用时，不隐藏其他独立主题；
- 质量不足时显示限制说明，而不是显示空白或伪造的 0；
- 重试只能重新请求 AI，不重新写入或修改 `RideRecord`。

## 12. 当前实现状态与产品差异

### 12.1 已实现的核心链路

- `RideRecord -> AnalysisContext -> eligibility -> interpretation plan -> model input` 链路已存在；
- Activity metric、Feature、Advanced claim 均有独立来源和证据；
- 上下文校验会拒绝旧 `dataLevel` 字段；
- 隐私排除、不可用原因、限制和 fallback 合同已保留；
- AI 输出失败不会回写详情事实。

### 12.2 当前调用链限制

当前骑后 AI API 构建上下文时主要调用 `buildRideAnalysisContext(record)`，没有在该入口传入 Profile 或历史比较快照。因此产品上应明确：

- 详情页可能根据客户端 Profile 计算心率区间或功率派生项；
- 这些结果不代表本次 AI 请求一定收到了相同的 Profile 数据；
- FTP、体重、最大心率和历史变化是否进入 AI，取决于后续调用方是否显式传入并通过上下文筛选；
- 不能因为详情页显示了某字段，就验收为 AI 已经使用了该字段。

该差异是后续 AI 解读重构的产品决策输入，不在本文件中自动视为已解决。

## 13. 产品验收规则

### AC-01 上下文来源正确

给定一条有效 `RideRecord`，上下文能够区分设备记录、确定性计算和估算指标，并保留来源与证据。

### AC-02 缺失不伪造

删除某项指标或使质量不通过时，该指标不以 0 或默认值进入 `allowedClaims`；对应能力或特征记录不可用原因。

### AC-03 单项隔离

功率不可用时，AI 不能谈功率，但仍可使用距离、速度或地形等独立有效事实。

### AC-04 规则结果可追溯

第 7 节生成的 Claim 必须带规则版本和 evidence；设备 NP 与序列重算 NP 不得无来源混用。

### AC-05 隐私边界有效

模型输入不包含原始轨迹、精确坐标、上传文件名和未受信任自由文本。

### AC-06 Profile 依赖真实

没有用户确认 FTP 时，不得生成或引用依赖 FTP 的功率区间、IF、TSS；没有体重时，不得生成 W/kg。

### AC-07 维度筛选有效

缺少某个解读维度的事实或性能证据时，该维度不进入模型输入，并留下排除原因。

### AC-08 降级不污染详情

上下文不合格、AI 关闭、Provider 失败或输出校验失败时，返回约定的降级状态，详情页原始事实和确定性分析不被覆盖。

### AC-09 不恢复旧分级

上下文、资格和候选输入中不得重新引入 `dataLevel` 或用 L1/L2/L3 作为骑行事实权限控制。

## 14. 待产品确认的问题

以下事项属于后续 AI 解读规则重构的决策点：

1. 骑后 AI 是否必须使用与详情页相同的 Profile 快照；
2. 历史比较是否进入默认骑后解读，还是只在用户主动请求时进入；
3. 详情页已经展示但 AI 未消费的字段，哪些应提升为 AI 事实；
4. 第 7 节高级分析中，哪些内部字段需要成为用户可见解释证据；
5. “部分缺失”结果的统一用户文案和可接受的 AI 表达强度；
6. AI 解读是否需要独立的业务场景版本，而不是只沿用详情页规则版本。
