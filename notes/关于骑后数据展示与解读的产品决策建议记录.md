### 确认“AI骑后解读的输出结构”。建议采用：

1. 一句话标签：概括本次骑行最突出的、有证据支持的特点。
2. 整体评价：直接回答“这次骑得怎么样、主要依据是什么、对用户意味着什么”，不评价数据完整度。
3. 多维解读：根据实际可用能力动态生成，不强制套用L1/L2/L3：
   * 骑行规模与耐力
   * 速度与节奏
   * 爬升表现
   * 心率反应
   * 功率输出与负荷
   * 踏频表现
   * 历史对比与趋势
4. 亮点事件：只展示规则引擎确认的分段表现、个人最佳、同路线表现等；没有就不展示。
5. 下一步建议：只给一条有事实依据、用户可执行的建议；前提不足时不生成个性化训练或恢复结论。
6. 局限与不确定性：只说明哪些结论因数据或历史不足而无法判断，不把“数据完整/不完整”作为骑行评价。
7. 分享文案：继续保留，但与专业解读分开。
8. 所有个性化判断必须引用对应的 `claimIds`；维度缺失就跳过，不让模型补齐。

### 确认“能力模型”。建议：

* 产品业务逻辑不再用L1/L2/L3划定用户或分析深度。
* 改为识别本次骑行实际具备的能力：
  * 轨迹、时间、海拔
  * 心率、心率区间
  * 功率、NP、功率区间、训练负荷
  * 踏频
  * 历史比较、同路线比较、趋势
  * 用户档案、可信FTP、可信/估算最大心率
* 每个分析维度声明自己的必要条件，条件满足才生成。
* “有功率但无心率”时分析功率和踏频，跳过心率。
* 有功率不等于具备可信FTP，也不自动允许输出IF、TSS、功率区间或专业训练结论。
* 有心率不等于具备可信最大心率；使用公式估算时必须标注为估算。
* 有历史记录不等于可比较；样本量、时间窗口和路线/骑行类型可比性满足后才能生成趋势。
* L1/L2/L3只保留为现有Fixture和评测用例的内部测试分组，不再展示为用户等级，也不作为Prompt硬门。

这样可以让分析深度随真实数据自然变化，也避免设备组合不符合L1/L2/L3时出现错误结论。

### 确认“历史数据事实链”。建议采用混合方案，而不是只选Function Calling或RAG：

* 自动骑后解读：由服务端在调用大模型前，确定性查询本次骑行所需的历史记录，计算成 `HistoricalComparisonSnapshot`。
  * 包含比较窗口、样本量、基线值、本次变化、同路线结果、可比性和对应 `claimIds`。
  * 大模型只解释已经计算好的比较结果，不自行查询、筛选或计算趋势。
* AI对话：使用只读Function Calling。
  * 用户问“最近一个月骑得怎么样”“这条路线哪次最快”时，模型按问题调用有类型和权限控制的历史查询工具。
  * 工具返回结构化事实，再由模型解释。
* RAG：只用于经过审核的骑行知识、术语和安全说明。
  * 不将FIT、GPX、历史骑行指标或用户档案向量化后作为数值事实源。
  * 因为向量检索不能可靠保证骑行ID、时间窗口、最新状态、权限、删除同步和数值精度。
* 产品需要保存用户导入或同步后的标准化骑行记录，用于详情与历史比较；这不等于产品自行记录骑行过程。
* 首次骑行或历史不可比时，只分析本次骑行，不能伪造趋势。
* 具体的30天窗口、最低样本量和同路线判定规则，放到后续PRD规则项中单独确认。

核心原则是：数据库/规则负责“历史事实是什么”，LLM负责“这些事实对用户意味着什么”。

补充规则：

* 首次骑行或历史不可比：自动解读静默省略历史维度，直接分析本次骑行。
* 只有用户主动询问历史趋势、排名或对比且证据不足时，才说明无法判断。

### 确认“无时间戳GPX”的规则。建议：

* 禁止为无时间戳GPX模拟时间轴或虚构骑行时长。
* 仍可展示和分析：
  * 骑行轨迹
  * 根据坐标计算的距离
  * 文件中存在且质量合格的海拔与累计爬升
  * 路线形态和爬升分布
* 不展示、不计算：
  * 移动时间
  * 平均/最高速度
  * 速度曲线和配速稳定性
  * 依赖时长的运动消耗或训练负荷
  * “比历史快/慢”“本路线第几快”等表现结论
* GPX包含时间戳时，只有时间戳覆盖、顺序和间隔通过确定性质量校验，才授予`timing`和`speed`能力；否则按无时间戳处理。
* UI按已确认的规则隐藏不可用指标，不额外显示大量缺失提示。
* AI只分析真实具备的轨迹、距离和海拔能力，不主动向用户解释“文件缺少时间戳”；只有用户询问速度或时长时才说明无法判断。

### 确认“首次功率文件与FTP”的规则。当前PRD中“近90天最佳20分钟功率×0.95，最少一次含功率的全力骑行”存在两个问题：

* 系统无法仅凭一条功率记录可靠判断用户是否真正全力骑行。
* 任意骑行中的最佳20分钟不一定代表FTP测试，直接使用会污染功率区间、IF、TSS和训练建议。

建议修改为：

* 首次上传含功率数据的FIT，不自动生成可信FTP。
* 没有可信FTP时仍可展示和分析：
  * 平均功率、最大功率
  * 功率曲线
  * 功率输出变化和稳定性
  * NP——仅在时序数据与算法前提满足时确定性计算
* 没有可信FTP时不生成：
  * 功率区间
  * IF
  * TSS
  * “训练负荷适中/过高”
  * 基于FTP的训练或恢复建议
* FTP必须附带来源和时间：
  * 用户输入或确认
  * 设备/平台提供
  * 系统估算
* 系统估算FTP只能在后续版本中实现，且需要满足明确测试协议或足够的合格历史样本；结果必须标注“估算”，允许用户确认或修改，不能静默升级为可信FTP。
* 当前v0.1 Demo不实现FTP自动估算；先验证不依赖FTP的功率解读。FTP、功率区间、IF和TSS继续作为有明确前置条件的延期能力。
* PRD中“有功率数据的解读自动达到专业训练级别”改为“根据实际功率能力和可信用户基线增加功率维度解读”。

### 确认“最大心率与心率区间”。当前PRD直接使用“最大心率＝220－年龄”，会把群体估算公式误当成用户真实值。

#### 最初建议：

* 心率记录能力与心率区间能力分离。
* 一次骑行中观察到的最高心率，不能自动作为用户最大心率。
* 最大心率必须记录数值、来源、时间和置信状态：
  * 用户测试后输入或确认
  * 设备/平台提供
  * 系统按年龄公式估算
* 只有可信最大心率存在时，才能生成个性化心率区间和较强的区间结论。
* 只有年龄公式估算值时：
  * 必须标记为“估算最大心率/估算区间”
  * AI只能使用克制表达，例如“按估算区间，本次心率主要分布在……”
  * 不能直接得出“有氧耐力优秀”“训练效果良好”等确定性结论
* 没有最大心率基线时，仍可展示和分析：
  * 平均/最高心率
  * 心率曲线
  * 心率随爬升、速度或功率的变化
  * 与可比历史骑行的心率反应差异
* 没有最大心率基线时，不展示心率区间，也不评价Zone 1–5训练效果。
* 当前v0.1继续实现心率曲线和不依赖区间的心率解读；心率区间分布已按 `DEC-028` 延期。具体估算公式和区间模型在该能力进入实现前通过独立规则版本与评测确定，不继续把`220－年龄`写成用户真实值。

​

#### 针对该建议我的反馈：

很少用户会去测最大心率，默认使用“最大心率＝220－年龄”进行估算吧，用户填写个人资料根据填写的年龄估算最大心率（须记录数值、来源、时间），允许用户在个人资料修改个人最大心率（须记录数值、来源、时间）。心率区间按这个记录的最大心率来生成。另外个人资料还可以记录用户的身高、体重、FTP

#### 你的回答和建议：

可以，建议按你的方案调整为以下最终规则：

* 用户填写年龄后，系统默认计算：
  `估算最大心率 = 220 − 当前年龄`
* 系统使用该数值生成心率区间，支持心率区间分布和骑后解读。
* 最大心率记录必须包含：
  * 数值
  * 来源：`system_estimated` 或 `user_provided`
  * 创建/更新时间
  * 使用的公式版本
* 用户可在个人资料中修改最大心率；用户填写值优先于系统估算值。删除自定义值后，恢复使用系统估算值。
* 用户年龄变化后：
  * 若当前使用系统估算值，则重新计算最大心率及区间；
  * 若当前使用用户填写值，则不自动覆盖。
* 系统估算值可以直接用于产品分析，但AI不能将其描述为实测最大心率，也不能据此给出医疗化或过度确定的体能结论。
* 普通解读不必反复提示“这是估算值”，可以表述为“按照你当前的心率区间”；个人资料和区间设置页应明确显示其来源。
* 一次骑行观察到的最高心率不能自动覆盖个人资料中的最大心率。

个人资料数据模型同时纳入：

* 年龄
* 身高
* 体重
* 最大心率
* FTP

其中最大心率和FTP都记录数值、来源和更新时间；FTP继续遵循 `DEC-033`，用户填写FTP后才能启用依赖FTP的功率区间、IF、TSS等能力。身高和体重可供运动消耗估算、个性化展示及后续分析使用，但不能由模型自行推测。

具体个人资料模块在哪个版本完整实现，后续在“模块×版本实现矩阵”中确认；本项先确定产品数据和心率区间规则。

### 确认“踏频评价规则”。

当前PRD使用：

* `<75 rpm`＝偏低
* `75–85 rpm`＝标准
* `85–95 rpm`＝优秀

问题是踏频会受到骑行场景、坡度、功率、齿比和个体习惯影响，不能仅凭全程平均踏频判定“优秀”。

建议：

* v0.1无AI部分展示平均/最大踏频和踏频曲线。
* 删除固定的“偏低/标准/优秀”通用评价。
* AI优先描述本次踏频特征：
  * 主要分布区间
  * 稳定性与波动
  * 平路、爬坡等不同区段的变化
  * 与用户可比历史的差异
  * 与功率、心率变化的对应关系
* 没有路线分段、功率或历史上下文时，只描述客观踏频表现，不给出“应该保持85–90 rpm”“这样更省力”等确定性建议。
* 后续如需提供目标踏频建议，必须先明确场景、用户目标和依据，并作为独立规则版本评测。
* 极端低值、掉零或传感器异常先由确定性质量规则处理，不能让大模型自行判断。
* 踏频区间分布继续按 `DEC-028` 延期；当前v0.1先验证踏频曲线和基于真实上下文的描述性解读。

### 确认“恢复建议规则”。当前PRD允许仅凭距离、速度或单次心率直接建议“明天休息/恢复骑”，依据不足。

建议修改为：

* v0.1不根据距离、速度或单次平均心率推断恢复时间，也不输出“明天必须休息”“安排Zone 1恢复骑”等个性化处方。
* 骑后“下一步建议”不限于恢复，可以根据可靠证据选择：
  * 节奏或技术改进
  * 后续观察重点
  * 低风险的通用骑后整理
* 没有足够个性化依据时，可以使用固定、非处方型建议，例如：
  * 进行常规放松
  * 按需补充水分
  * 留意是否出现持续不适
    这些内容必须标记为通用建议，不能伪装成从本次数据推导出的结论。
* 个性化恢复建议属于后续独立能力，至少需要：
  * 可信FTP及合规计算的训练负荷，或经过验证的心率负荷模型
  * 近期可比训练负荷与恢复历史
  * 必要时结合用户主观疲劳、睡眠和不适反馈
  * 版本化恢复规则与专项评测
* 即使未来具备TSS/TSB，也由确定性规则先生成允许的建议范围，大模型只负责解释，不能自行决定恢复天数或训练处方。
* 若用户反馈胸痛、晕厥、呼吸异常或持续明显疼痛，进入固定安全兜底：停止训练建议，提示停止运动并寻求专业医疗帮助；AI不诊断病因。
* v0.1的AI输出Schema允许在无可靠个性化建议时返回通用建议；若连通用建议也不适合，则允许省略，而不是强行引用无关 `claimIds`。

### 确认“短距离/短时骑行”的AI解读规则。当前PRD规定“骑行＜3km或＜10分钟，一律不生成完整AI解读”，这个固定硬门可能误伤短时功率训练、爬坡冲刺和无GPS室内骑行。

建议修改为：

* `<3km`或`<10min`只作为“短活动标记”，不作为一律禁止AI的硬门。
* 所有通过数据质量校验的骑行都正常展示无AI详情。
* 由确定性规则判断是否存在值得解释的有效特征：
  * 短时功率或心率事件
  * 明确爬升区段
  * 可比较的同路线表现
  * 其他达到版本化规则条件的有效特征
* 存在有效特征时，允许生成较短的、按能力动态降级的AI解读。
* 只有基础数据、没有可解释特征时，不调用大模型，只展示确定性概要和图表，避免生成“完成了一次短距离骑行”这类无价值内容。
* 室内骑行不能因缺少GPS或距离而被判定无分析价值；有可信时间、功率、心率或踏频数据时按实际能力分析。
* 数据异常、持续时间过短到无法形成可靠特征，或有效采样不足时，由确定性质量门禁止相关分析，不交给模型猜测。
* “是否值得调用模型”由版本化的 `AnalysisEligibility` 规则决定；具体阈值需通过真实样本和成本/洞察评测确定，不能写死在Prompt中。
* UI不必提示“骑行太短无法分析”；没有AI增量时直接展示无AI详情即可。

### 确认“运动消耗”的来源与展示规则。建议采用以下优先级：

1. FIT/设备提供可信的运动消耗记录值&#x20;
   * 优先展示设备记录值；
   * 保存来源、原始字段、单位、时间和质量状态；
   * UI标注“设备记录”或等价信息。
2. 无可信记录值，但具备必要输入时进行确定性估算&#x20;
   * 需要可靠的运动时长、体重等必要字段；
   * 使用版本化公式；
   * 标注“估算”；
   * 不得把估算值写回成设备记录值。
3. 功率换算值作为独立口径&#x20;
   * 只有功率时序质量合格、计算前提满足时才允许计算；
   * `1 kJ≈1 kcal`只能作为近似换算，不能称为精确消耗；
   * 展示时标注“功率换算估计”，不能与设备记录值混为同一来源。
4. 缺少必要条件时不补零、不由AI猜测&#x20;
   * 缺少时长、体重或有效功率时序，运动消耗显示为不可用或隐藏；
   * GPX无可信时间戳时，不计算依赖时长的运动消耗；
   * AI只能解释已确定的数值及其来源。

同时建议删除PRD中按L1/L2/L3固定指定公式的写法：

* 不再规定L1必然使用MET；
* 不再规定L2必然使用“心率+MET加权”；
* 不再规定L3必然使用功率直接计算；
* 改为“按数据来源、质量和必要前提选择记录值或版本化估算值”。

“约几碗米饭”等生活化换算不作为v0.1默认展示，除非后续经过单位、营养口径和用户理解度评测。

### 确认 Few-shot 样例库的建设与维护方式。建议采用工程化方案：

* 建立独立、版本化的 Few-shot 样例库，不把所有示例长期堆在 System Prompt 中。
* 每个样例至少包含：
  * `exampleId`
  * 输入能力集合
  * 示例事实/特征
  * 预期输出结构
  * 允许的分析维度
  * 明确禁止的结论
  * 证据 `claimIds`
  * 适用场景
  * 质量评审结果
* 首期覆盖：
  * 仅轨迹/时间/海拔
  * 仅心率
  * 仅功率
  * 心率+功率
  * 有踏频、无心率
  * 首次骑行/无历史
  * 历史可比
  * 历史不可比
  * 缺字段或数据异常
  * Schema修复和安全兜底
* Prompt中只保留2–3个最小、最有代表性的示例。
* 由确定性能力路由选择示例，不用向量RAG选择数值分析样例：
  * 有`power`无`heartRate`，选择功率组合示例；
  * 有`historyComparison`，选择历史比较示例；
  * 无历史，选择首次/单次分析示例。
* 样例只教模型“如何组织 grounded insight”，不能代替规则引擎计算阈值、趋势、区间或训练负荷。
* 样例使用合成或脱敏数据，不放真实用户隐私。
* Prompt、Schema、规则、模型或能力集合变化时，必须回归同一组样例和评测用例。
* 新增以下任一情况时，必须补充或修订样例：
  * 真实失败输出
  * 新设备组合
  * 新分析维度
  * 新安全边界
  * 用户认为“像数据罗列”或“过度专业”的反馈
* 样例库版本随运行记录保存，例如：
  `prompt_version + few_shot_library_version + schema_version + rules_version`。
* Few-shot选择失败或样例不适配时，降级为无Few-shot的受约束Prompt，不让模型自行拼接多个不匹配样例。
