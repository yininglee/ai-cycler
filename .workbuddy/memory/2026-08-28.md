## AI 骑行数据管道：笔记概念 ↔ 真实代码映射

用户要求"层级之间是怎么工作的？基于当前项目代码分析并可视化"。基于 `notes/AI骑行伙伴-数据处理与原子能力学习笔记.md` 对照 `src/` 实际代码，结论是：数据管道是一串**纯函数 + 类型化契约 + 校验闸门**，向前不可变流动，无共享可变状态。

真实调用链（文件名即层级）：
- `parsers/index.ts: parseRideRecord` → `RideRecord{activity,series}`
- `domain/atomic-capabilities.ts: buildAtomicCapabilityProfile` → `AtomicCapabilityProfile`（18 能力，含 available/unavailableReason/dependencyKeys；heartRateZones/powerZones/trainingLoad/trend 即使依赖齐全也标 RULE_NOT_IMPLEMENTED）
- `domain/ride-features.ts: buildRideFeatureSnapshot` → `RideFeatureSnapshot`（features[]+unavailable[]，带 formulaVersion；MIN_STAT_SAMPLE_COUNT=5, MIN_SEGMENT_SAMPLE_COUNT=8）
- `domain/ride-analysis-context.ts: buildRideAnalysisContext` ◀ 聚合枢纽：把 metrics + featureSnapshot + history + capability 合并去重成 `allowedClaims`；cap=false→forbiddenClaims，unavailable→limitations，privacyFlags 常驻
- `domain/analysis-eligibility.ts: buildAnalysisEligibility` ◀ 准入控制：先 `validateRideAnalysisContext`，再据 feature/history 推导 allowedDimensionKeys / requiredClaimIds / fallback(b0|safety_stop)
- `ai/ride-analysis-context-projection.ts: projectRideAnalysisContextForModel` ◀ 瘦身：只留 allowedClaims+forbidden+limitations+safetyFlags+privacyFlags，丢弃 metrics/featureSnapshot/capabilities/history
- `ai/coze-workflow-client.ts: provider.run` ◀ 唯一模型调用；内部再次 project
- `ai/ride-analysis-output-v03.ts: validateRideAnalysisOutputV03` 校验；失败一次 repair（repairInstruction 禁新增事实）→ 仍失败 b0
- 编排：`ai/ride-analysis-service.ts: analyzeRideRecord → prepareRideAnalysis → runRideAnalysis`

关键发现：**展示值（displayValue/displayUnit）已在 `buildRideAnalysisContext` 的 `displayFields()` 由服务端算出（metric-display-v0.1）**——笔记 §6.3 称"尚未正式加入" 已过时，需更新笔记。

可视化用 3 张内联 SVG 呈现：真实代码调用链、allowedClaims 聚合枢纽、投影瘦身+服务端循环。
